Product thesis

Magic on the surface; evidence underneath. Noesis should become better during normal use without asking the user to operate a learning pipeline. The user may inspect, guide, veto, pin, approve authority expansion, or revert an active revision at any time.

LLMs do semantic work

Signal interpretation, reflection, hypothesis formation, capability-revision authoring, case generation, judging, revision, and explanation.

Code holds thin rails

Transactional operational state, file revisions, provenance, authority, bounded execution, activation, and reversion remain dependable while research objects evolve quickly.

Stable capability, evolvable revisions

A Capability names a learned behavior; each CapabilityRevision couples its concrete prompt, skill, tools, router, activation, and permission implementation.

ordinary work
  → evidence signals
  → LLM reflection: no_change | experiment brief
  → candidate CapabilityRevision authored
  → lightweight preflight against the baseline revision
  → low-risk automatic activation
  → open experiment gathers real-world feedback
  → keep, revise, or revert

Research-preview posture

Optimize for learning velocity. Noesis is a research system before it is a hardened platform. Prefer the smallest credible experiment that can produce a trace, a comparison, and a user-visible result. Harden a seam after evidence shows it matters.

LLM-pilled by default

Use capable models for interpretation, search planning, hypothesis formation, capability-revision authoring, case generation, judging, routing, explanation, and revision. Deterministic code supports the loop; it does not replace semantic intelligence.

Experiments are products

Every research idea should be runnable against a baseline, preserve its prompt/model/policy choices, and produce comparable traces and artifacts that can inform the next experiment.

Rigidity must earn its keep

Internal TypeScript objects evolve freely. Add validation, versioning, packages, statistical ceremony, or stronger isolation only at a real boundary or when an experiment demonstrates the need.

Deep modules with earned boundaries

A concept starts as a package-local file beside its first consumer. It becomes a package only when multiple real consumers need a stable boundary or the runtime needs independent process ownership. This keeps the research loop malleable without collapsing the important Pi, workspace, authority, and generated-code boundaries.

@noesis/workspace

WorkspaceStore owns SQLite transactions and migrations, canonical file locations, file revision/activity metadata, artifact metadata, backups, and the one-authority-per-datum rules.

@noesis/agent-types

Small adapter-neutral types and ports for model roles, tools, traces, usage, and experiments. AC-00 creates the package from the needs of the parallel foundation consumers; later tasks extend it only through a shared metadata barrier. It imports no Pi types.

@noesis/intelligence

Hybrid history search over authoritative SQLite session/message/tool/outcome rows and canonical file revisions. FTS, embedding, and search-document rows are rebuildable indexes that always cite those canonical sources.

@noesis/tool-runtime

Out-of-process generated code host, exact dependency locks, schemas, resource limits, and EffectGateway mediation.

@noesis/background

Created only when runtime and the resident worker both consume durable work orchestration; until then, opportunistic coordination stays inside runtime.

@noesis/learning

Signals, LLM reflection, hypotheses, experiment briefs, source cases, and capability-revision authoring.

@noesis/evals

Generated cases, paired trials, a swappable judge/critic, protected gates, comparison reports, and optional advanced policies.

@noesis/capabilities

Stable capability identities, candidate and active revisions, activation policies, pins, vetoes, and SQLite activation pointers.

@noesis/runtime-pi

The only Pi import boundary. Implements foreground and isolated role execution plus the generated-tool adapter.

@noesis/runtime

Adapter-neutral turn orchestration, frozen intelligence plans, coordinator, activation decisions, experiment outcomes, and continuous feedback.

@noesis/tui

Ephemeral read models: chat, learning activity, changes, evidence, experiments, approval, pin, veto, and revert.

Generated behavior can propose arbitrary tool code and mutable prompt layers, but cannot modify the protected kernel, authority, workspace ownership rules, activation rails, evaluation evidence, or its own permission manifest. Evaluation strategies are experimental; the separation between generated revision authorship and protected activation authority is not.

A capability is the stable deployable behavior; a revision is one concrete implementation. An experiment is a durable learning episode connecting the reflection hypothesis, baseline and candidate revisions, preflight, activation, real-world feedback, and final outcome. Experiments never become capabilities and are never activated. Product behavior changes normally create capability revisions; experiments may also compare internal research strategies without creating a user-facing capability.

A coupled revision is preflighted from stable snapshots. Protected activation reloads a recorded passing preflight report, recomputes the canonical digest of the complete materialized CapabilityRevision, and requires it to match the report's candidate identity. Activation then uses one SQLite transaction to make that exact prompt/tool/router revision set visible and update the activation pointer. Abandoned staged revisions are inert and cleanable.

Prompt ownership layers

  1. Protected kernel: code-owned authority, provenance, credential, and dangerous-effect rules.
  2. User constitution: explicit user-owned instructions; no silent learned rewrite.
  3. Learned profile: automatically evaluable style, reasoning, teaching, and workflow modules.
  4. Capability layer: modules tied to selected active capability revisions.
  5. Retrieved context: bounded history/memory fragments with exact citations and untrusted-data framing.
  6. Turn context: current session, artifacts, tools, and request.

The experiment stays open after activation so real use can confirm, refine, or reverse the hypothesis. revise authors a follow-up capability revision and experiment; revert restores the prior activation.

Signal harvesting

Store sessions, messages, tool calls, usage, latency, steering, aborts, retries, follow-ups, corrections, and outcomes in SQLite. Put large raw traces and outputs in artifact/evidence files and reference them from their operational rows.

Reflection trigger

Explicit correction, recurring workflow/failure, friction, surprise, capability gap, cost anomaly, preference change, or direct request. No useful change is a first-class outcome.

Transactional state and lightweight activity

SQLite rows own the current lifecycle state for jobs, capabilities, revisions, experiments, trials, preflights, approvals, and activations. Each meaningful transition updates its row transactionally and writes a concise activity_log entry with actor, kind, subject, timestamp, and references. Activity is for provenance, debugging, and UX feeds; current state is read directly from the owning table, never reconstructed from activity.

A working-file edit first snapshots its bytes into the revisions area with content digest and predecessor. One SQLite transaction then registers the revision and updates any visible pointer. A staged snapshot abandoned before that transaction is inert and eligible for cleanup. Agent-authored material always lands in candidate directories; active definitions stay separate. Evaluations and turns pin stable revision snapshots, never mutable working-file bytes. Raw cases, trial outputs, tool traces, judgments, and reports create new evidence revisions.

The activity log is deliberately not a universal change journal. Recovery uses SQLite transactions, migrations, integrity checks, and backups; declarative recovery uses the canonical files and their revision history. Evaluation evidence is append-only so neither Noesis nor an external editor can silently alter the basis of a prior activation or outcome.

Longitudinal intelligence and session search

  • SQLite is authoritative for sessions, messages, tool calls, outcomes, and operational search configuration.
  • FTS5 retrieves exact lexical evidence and stable session/message/tool-call IDs.
  • Local embeddings provide semantic recurrence without sending the full history to a provider.
  • FTS, embedding, and search-document rows are rebuildable indexes whose source reference is always an authoritative DB row or canonical file revision.
  • File-backed profile, memory, prompts, skills, tools, and eval definitions are indexed from their canonical recorded revisions, never unpinned mutable bytes.
  • An LLM search planner/reranker receives only bounded candidates and returns a typed ranking with reasons.
  • Every result carries a session/message row reference or file/evidence revision, timestamp, excerpt, retrieval scores, and provenance.
  • Retrieved history is untrusted context, never protected instruction.

Paired execution

  • Give the baseline and candidate the same task evidence and a comparable execution budget; record any intentional model or runtime difference as the experiment variable.
  • Run the arms independently, randomize their labels for the judge, and ask for evidence-backed criticism rather than a bare score.
  • Retain outputs, artifacts, tool/effect traces, usage, latency, and failures so later real-world outcomes can audit the judgment.

Optional user criteria, captured conversationally

  • Explicit normative statements such as “always preserve my voice” and direct corrections become scoped active criteria with exact session/message or file-revision citations. The normal interaction receives only a quiet summary; no setup flow or approval prompt interrupts the user.
  • Ambiguous or inferred preferences remain tentative profile/memory observations until corroborated. Editing or retiring a criterion never rewrites its prior revisions or the evaluations that used them.
  • For each candidate, relevance selection produces a criterion snapshot. The case generator uses it to create targeted cases, and the judge/critic reports which criterion ID, revision, instruction, and evidence it applied.
  • Pinned criteria cannot be silently superseded. The expert surface can add, edit, retire, or pin criteria without making routine learning interactive.

Continuous feedback and experiment outcomes

  • Observe continuously: attribute corrections, retries, aborts, follow-ups, explicit feedback, artifact acceptance, effects, errors, cost, latency, context, activation quality, and user-policy compliance to the serving revision and open experiment.
  • Keep: close the experiment while leaving the revision active when preflight and real-world evidence support the hypothesis.
  • Revise: close with a documented learning, author a successor revision, and connect a follow-up experiment to the original lineage.
  • Revert: restore the previous activation as the outcome action when evidence shows a hard failure or convincing regression.

Research runtime, authority, and progressive hardening

Generated-code research backend

The first backend runs a local child process in a fresh temporary directory with a sanitized environment, bounded time and output, declared effects, and brokered Noesis tools. Capture source and execution artifacts. This is explicitly not a production security boundary; use it for trusted local research, and never auto-grant dangerous external effects.

Evaluator isolation

Candidate authors do not receive judge decisions or hidden protected cases. Judges receive escaped artifacts and randomized arms. Role context separation reduces gaming, while stronger process/storage isolation remains a hardening option.

Idempotent orchestration

Each durable work item has a stable identity and a minimal operation fingerprint. Reservation precedes dangerous external execution; ambiguous external effects fail closed without forcing every internal research object into an identity graph.

Crash recovery

Expired leases retry safe work. Ambiguous paid LLM attempts consume a new explicit attempt budget. SQLite corruption restores from a verified backup; missing declarative files or artifacts are reported rather than fabricated from activity history.

Generated tools communicate over bounded stdio JSON-RPC with a trusted broker for declared capabilities. The broker validates boundary payloads and asks EffectGateway to authorize dangerous external effects; workers never receive authority handles or receipts. The runtime backend remains a port so later experiments can swap in a container, VM, or OS sandbox without changing capability authorship or evaluation.

Progressive hardening ladder

  1. Research preview: temporary-directory child process, sanitized environment, limits, brokered tools, explicit approval for dangerous effects.
  2. Evidence-driven isolation: Node permissions, containers, or OS sandbox backends for experiments that execute less-trusted code.
  3. Production hardening: reproducible builds, dependency policy, SBOMs, read-only materialization, registry controls, fuzz/property suites, and stronger evaluator isolation.

Verification and research feedback

Boundary tests

  • Config v1, SQLite migrations, transaction constraints, and backup restore
  • One declared authority for every persisted datum
  • Direct file edits snapshot immutable revision bytes with digest/predecessor; prior pins still resolve identically
  • Search indexes can be deleted and rebuilt from canonical DB rows and file revisions
  • Source-only author boundary
  • Role context isolation
  • Candidate/active directory separation and atomic activation pointers
  • Staged revision failure before pointer commit is inert and cleanable
  • Pin/veto and autonomy decisions
  • Effectful operation identity and retry behavior
  • AST and package-manifest dependency direction; runtime cannot import runtime-pi

Evaluation tests

  • Comparable baseline/candidate inputs with the experiment variable recorded
  • Blind labels and evidence-backed judge criticism
  • Prompt injection cannot grant authority or alter protected rails
  • Protected rails override qualitative wins
  • Candidate revision changes invalidate its preflight report
  • Negative reports remain queryable
  • Evidence used by a decision cannot be overwritten; corrections create revisions

Focused failure paths

  • Malformed LLM output, timeout, rate limit
  • Restart around queue reservation and activation
  • Tool crash, hang, and oversized output
  • SQLite restore, missing file reference, and orphan artifact metadata
  • Ambiguous dangerous external effect

Exhaustive interleavings, fuzz/property suites, and hardened-runtime penetration tests are progressive hardening, not preview launch gates.

CI rules

  • Fake role runner and fake generated-tool backend cover the core loop.
  • No provider login or paid call is required.
  • Run format, lint, typecheck, tests, and architecture checks.
  • Workspace fixtures prove SQLite/file authority, migration, evidence revisions, and backup restore.

Definition of done

  1. Session A: the user corrects Noesis during ordinary work and explicitly says “always preserve my voice”; no learning or criteria command is issued.
  2. Noesis captures the scoped criterion with its correction citation and shows only a quiet summary; /criteria can inspect, edit, retire, or pin it later.
  3. Noesis automatically searches prior sessions, detects recurrence, and records exact evidence citations.
  4. LLM reflection returns an evidence-linked hypothesis/experiment brief, then authors a candidate capability revision coupling a learned prompt module, generated tool code, and routing rule.
  5. The tool runs in the bounded local preview backend. A criteria-off versus criteria-on fixture proves that activating the voice-preservation criterion adds targeted generated cases and changes the judge rubric.
  6. Baseline and candidate run blind paired trials; one strong judge/critic prefers the candidate, cites the applied criterion revision and evidence, and protected rails pass.
  7. The low-risk capability revision activates automatically by staging stable active-revision bytes, then atomically exposing the complete revision set and updating the SQLite activation pointer; its experiment remains open.
  8. Session B: relevant history is retrieved with exact citations and the router selects the new active capability revision.
  9. /why shows evidence, baseline/candidate variants, judge reasoning, permission manifest, and exact active revision IDs.
  10. Real-world feedback is attributed to the active revision and open experiment; a seeded regression resolves it as revert and automatically restores the prior activation pointer, while a separate fixture proves revise creates linked successor revision and experiment.
  11. A direct user edit remains the canonical working file, creates a new stable revision without changing prior pinned bytes, refreshes rebuildable search indexes, and invalidates stale evaluations without copying definition content into SQLite.
  12. SQLite backup/restore recovers sessions, jobs, experiments, evaluations, search configuration, and activation pointers; FTS/embedding/search-document indexes rebuild from canonical DB rows and file revisions.
  13. The entire journey passes with fake models and tools in CI, followed by a green pnpm check.
The user experiences a capable agent that quietly becomes better. The system retains enough evidence to explain exactly why it changed, what won, what authority it has, which version served a turn, and how to reverse it.
