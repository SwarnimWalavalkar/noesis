Implementation plan · decided architecture

The capability loop

Replace the ceremony-heavy adjustment → experiment → candidate → preflight → activation pipeline with one transparent, versioned Capability that Noesis can create, activate, improve, pause, and restore through real work with the user.

Optimize for the shortest recoverable loop:
observe → create or revise a capability → put it into real use → learn from feedback → keep, iterate, pause, or restore.

1. Decisions

One product noun The durable, user-facing abstraction is Capability. Working adjustment, experiment, candidate, and activation no longer describe separate product lifecycles.
Global by default New capabilities are globally eligible unless the model or user chooses a project or session scope. Global eligibility does not mean unconditional prompt injection.
Relevant or always Each active binding is either selected semantically when relevant or mounted on every eligible turn. The user can change this at any time.
Reflect every turn There is no preliminary “useful work” classifier. Every admitted foreground turn that settles runs the same reflector and may return no_change.
Real use is the loop Ordinary capabilities activate without preflight. User feedback and later ambient reflection drive iteration and recovery.
Evaluation deferred This implementation creates no new evaluation system. Existing evaluation records stay readable as history; future real evaluation is a separate design.
No usage ledger A Capability does not own a row for every turn that selected it. The frozen turn plan already pins exact revisions, so usage can be derived later if it is ever needed.
Small consequence gate Only autonomous activation that threatens recovery or causes an irreversible external consequence pauses for approve, deny, or change.

2. Product contract

Noesis may autonomously change meaningful parts of its harness, including prompts, skills, tools, workflows, routing, model configuration, and authority configuration. The ordinary safety mechanism is visible provenance plus fast iteration and exact restoration—not a mandatory speculative evaluation pipeline.

  • A Capability can become active as soon as its exact revision is recorded and validated.
  • The default scope is global; the user can narrow it later.
  • The default activation mode is relevant; the user can make it always.
  • Every material activation, revision, pause, restoration, scope change, and gate decision is visible in /learning.
  • The user can give ordinary conversational feedback or manage the Capability directly in the TUI.
  • A revision never deletes its predecessor, its motivating evidence, or the recovery path required to undo it.
  • no_change remains a normal result but appears only as an aggregate health signal unless the user opens the complete audit view.

The intentionally changed doctrine

The implementation must update AGENTS.md, docs/product-thesis.md, docs/product-experience.md, and docs/agent-intelligence-and-experience.md before the new behavior ships. The following old rules no longer describe the product:

  • New learning always starts at the narrowest plausible scope.
  • Repeated evidence is required before global reach.
  • Generated learning cannot change tools, permissions, or authority.
  • Broader learned behavior must pass preflight and protected activation.
  • A project-only WorkingAdjustment is the sole immediate ambient-learning form.

This is not permission theatre. Noesis already operates with the user’s terminal and file access. The rearchitecture preserves durable effect settlement, idempotency, credential storage, audit, and recovery because they are operationally useful; it does not pretend they form a sandbox that the agent otherwise lacks.

3. The complete lifecycle

every admitted foreground turn reaches a terminal state
  → enqueue one durable capability reflection
  → reflector returns no_change | create | revise | restore | pause | change_binding

create or revise
  → simple revision returned directly, or specialized author materializes exact bytes
  → validate definition, dependencies, predecessor, and recovery information
  → consequence gate says automatic | user_decision

automatic
  → record immutable CapabilityRevision
  → compare-and-swap CapabilityBinding
  → emit transient TUI notification
  → revision becomes eligible for the next frozen turn

user_decision
  → /learning shows pending Capability
  → approve | deny | change in natural language
  → approve binds exact revision
  → deny retains the rejected revision and evidence
  → change authors a child revision and presents that exact child

later work
  → scope filter determines eligibility
  → “always” capabilities mount directly
  → capable router selects among “relevant” capabilities
  → FrozenTurnPlan pins exact selected revisions
  → user feedback or ambient reflection keeps, iterates, pauses, or restores

Exactly which turns reflect

Reflection runs once for every admitted user foreground turn after it reaches a durable terminal state:

  • completed, including turns with no tool calls;
  • failed, because failure can reveal a missing or harmful capability;
  • aborted, because the visible partial work and user interruption are evidence.

A queued prompt that has not been admitted is not a turn. Slash commands that only inspect or navigate TUI state do not reflect. Background jobs do not recursively create reflection jobs. There is no higher-level model call deciding whether work was “useful”; the reflector itself makes the only semantic decision and may cheaply return no_change.

The next turn in the same session waits only for the exact preceding reflection job up to the existing bounded deadline. It never waits for a general learning drain. A late result becomes visible to a later turn.

4. Capability model

Reuse and deepen the existing Capability and CapabilityRevision concepts. Do not introduce a parallel durable Change entity. WorkspaceStore remains the sole authority for operational bindings and lifecycle decisions; immutable file revisions remain authority for declarative bytes.

Capability

interface Capability {
  readonly capabilityId: string;
  readonly name: string;
  readonly kind:
    | "instruction"
    | "skill"
    | "tool"
    | "workflow"
    | "router"
    | "model_configuration"
    | "harness_configuration"
    | "core_update"
    | "composite";
  readonly description: string;
  readonly applicability: string;
  readonly createdAt: string;
}

applicability is a concise semantic description of when the Capability helps. It is used by the capable router. It is not a regex, tag match, or keyword classifier.

CapabilityRevision

interface CapabilityRevision {
  readonly capabilityRevisionId: string;
  readonly capabilityId: string;
  readonly predecessorRevisionId?: string;
  readonly summary: string;
  readonly rationale: string;
  readonly anticipatedEffect: string;
  readonly materials: readonly CapabilityMaterialRef[];
  readonly dependencyLock?: FileRevisionRef;
  readonly permissionManifest: PermissionManifest;
  readonly evidenceRefs: readonly EvidenceRef[];
  readonly createdAt: string;
}

A revision contains or references the exact implementation that can be mounted. Authoring always receives the complete predecessor materials. The revision is immutable once any binding or frozen turn references it.

CapabilityBinding

interface CapabilityBinding {
  readonly capabilityId: string;
  readonly revision: CapabilityRevisionRef;
  readonly scope:
    | { readonly kind: "global" }
    | { readonly kind: "project"; readonly project: ProjectRef }
    | { readonly kind: "session"; readonly sessionId: string };
  readonly activationMode: "relevant" | "always";
  readonly state: "active" | "paused";
  readonly revisionNumber: number;
  readonly updatedAt: string;
}
  • One current binding exists per Capability.
  • New bindings default to global and relevant.
  • Changing scope moves the binding; it does not clone the Capability.
  • always bypasses relevance selection but still obeys scope eligibility.
  • All mutations compare the expected binding revision in one SQLite transaction.

No Capability-use table

Do not add capability_uses, served-turn arrays, counters owned by the Capability, or a denormalized list of every turn that used a skill. The existing FrozenTurnPlan.selectedCapabilities already records the exact revision selected for a turn. A future audit query can derive usage from frozen plans and foreground turns.

The Capability stores motivating evidence and feedback that changed its lifecycle. It does not absorb every operational event merely because that event may later be useful for analytics.

CapabilityFeedback

interface CapabilityFeedback {
  readonly feedbackId: string;
  readonly capabilityId: string;
  readonly revision: CapabilityRevisionRef;
  readonly evidenceRefs: readonly EvidenceRef[];
  readonly interpretation: string;
  readonly disposition:
    | "positive"
    | "correction"
    | "regression"
    | "scope_change"
    | "activation_change"
    | "restore_request";
  readonly createdAt: string;
}

Feedback is recorded when it causes or credibly supports a lifecycle decision. Noesis does not manufacture a feedback row for every silent successful turn.

5. Model intelligence

Use capable models wherever meaning is required. Keep persistence, immutable identity, compare-and-swap, schema validation, and recovery deterministic.

Ambient capability reflector

The reflector receives:

  • the exact settled user and assistant messages, including unfinished-turn labels;
  • bounded tool calls, failures, outcome facts, and runtime telemetry;
  • the exact Capability revisions selected by the frozen turn plan;
  • explicit conversational feedback from the current turn;
  • bounded, opened cross-session evidence chosen for relevance;
  • active Capability descriptors and likely conflicts or overlaps;
  • the current binding and complete predecessor for any proposed revision;
  • the user’s direct remembered criteria when relevant.

Its structured decision is:

no_change
create_capability
revise_capability
restore_capability
pause_capability
change_binding

Every non-no_change result cites exact evidence and explains anticipated effect. The host rejects nonexistent, unauthorized, or sensitivity-incompatible citations.

Specialized author

A simple instruction revision may be complete in the reflection result. Tools, skills, workflows, routers, and configuration use a specialized author with:

  • the exact predecessor bytes and manifest;
  • the exact requested target and user amendment;
  • opened evidence excerpts rather than opaque evidence IDs;
  • available catalog, schemas, dependencies, and runtime constraints;
  • related active capabilities and known conflicts;
  • the required output schema for that Capability kind.

The author returns exact declarative materials. It never returns a digest standing in for behavior it has not seen.

Capability router

Before each turn, deterministic scope filtering partitions active bindings:

  1. Ineligible project or session bindings are removed.
  2. always bindings are selected directly.
  3. The existing capable router receives the request, bounded conversation, and descriptors of eligible relevant capabilities.
  4. The union is materialized and frozen into the turn plan.

The router records its reason, but no separate Capability-use record is written. The frozen plan is enough to reconstruct what the model received.

Feedback iteration

The external semantic interface is named iterateOnFeedback. It receives the user’s feedback, current conversation, candidate Capability targets, their exact active revisions, and the prior evidence. It returns: 

keep
revise
restore
pause
change_scope
change_activation_mode

Explicit feedback can run immediately. Otherwise it is folded into the ambient reflector for the current settled turn. Silence is not positive feedback, and code does not use keywords to infer corrections.

Calls removed from the ordinary loop

  • scope-verification call;
  • experiment-brief generation;
  • synthetic transfer-case generation;
  • baseline and candidate simulation calls;
  • blind judging over simulated artifacts;
  • preflight aggregation;
  • post-activation experiment outcome judging;
  • revision-agent successor experiment creation.

A normal turn therefore produces one reflection call and, only when necessary, one specialized authoring call. JSON repair remains bounded and explicit.

6. Activation and the tiny consequence gate

Activation is ordinarily an atomic binding update, not a promotion. Protected code validates exact revision identity, material availability, dependency integrity, and expected current binding before changing what future turns can mount.

Automatic activation

Automatic activation covers reversible capability changes, including:

prompts skills tools workflows routing model configuration harness configuration authority configuration

A tool is not gated merely because it is a tool. A global revision is not gated merely because it is global. A permission change is not gated merely because an older architecture labeled it protected.

User decision

An autonomous background activation requires a user decision only if the activation itself:

  1. removes or weakens audit, notification, restoration, or safe-mode recovery;
  2. can make the previous bootable runtime unrecoverable;
  3. exports credential values or changes credential ownership;
  4. performs an irreversible external action such as deletion, publication, deployment, purchase, or communication that the foreground request did not already authorize;
  5. changes the small gate that decides these exact cases.

Foreground user instruction supplies intent for the requested action and must not trigger a redundant learning approval.

The host imposes these few bootstrap constraints using exact owned resources and effect classes. The model supplies a consequence description but does not decide whether it may erase its own recovery mechanism.

Approve, deny, or change

  • Approve: bind the exact pending revision if the expected binding is unchanged.
  • Deny: retain the revision and evidence as rejected history.
  • Change: collect natural-language direction, author a child revision, and replace the pending request with that exact child.

A gate request never holds mutable generated bytes. It pins an immutable revision and expected current binding.

Learning outcomes are TUI notifications and Capability records, not assistant messages and not transcript notes. The conversation stays about the user’s work.

Capability detail

The normal view prioritizes:

  1. what the Capability does;
  2. what changed from the predecessor;
  3. why Noesis created or revised it;
  4. readable cited evidence with links to exact records;
  5. scope and relevant/always activation mode;
  6. current revision and prior restorable revisions;
  7. feedback that caused iteration, pause, or restoration;
  8. pending user decision and its consequence;
  9. validation, loading, or recovery diagnostics.

Raw IDs, JSON, legacy experiments, preflight records, and job data remain available in a bounded sensitivity-aware audit view. They do not dominate the product view.

Mutations

The TUI emits typed intents and waits for authoritative settlement. It never mutates local UI state optimistically as if the operation succeeded.

8. Recovery and failure behavior

Failure Required behavior
Reflection fails or times out The foreground turn remains complete. Record a quiet diagnostic; make no change.
Author returns malformed material Retain the current binding. Record the failed attempt and bounded error.
Dependency is missing or stale Do not bind the revision. Show the exact failed dependency in /learning.
Binding changed concurrently Return a stale result. Never overwrite the newer user or model decision.
Capability breaks turn planning If resolution identifies one invalid Capability, compare-and-pause that exact binding and retry. If the failure is an ambiguous composition failure, admit one genesis-only safe-mode plan for the session instead. Notify the user and preserve the failed planning diagnostic; do not invent a “last known good” ledger.
Capability behaves poorly User feedback or ambient reflection creates a child revision, pauses, or restores.
Process crashes during activation SQLite transaction leaves either the old binding or the complete new binding active.
Core runtime update cannot boot External boot selector restores the previous build. Learned source changes cannot own or delete that selector.

Repeated semantic mistakes are tolerable; being stuck is not. Operational recovery therefore receives more engineering investment than speculative pre-activation judgment.

10. Persistence and cutover

New authoritative tables

  • capabilities — stable identity and descriptive metadata;
  • capability_revisions — immutable revision envelope and material refs;
  • capability_bindings — one current scope/mode/state/revision per Capability;
  • capability_feedback — evidence-bearing feedback that affected lifecycle;
  • capability_gate_requests — immutable pending/settled user decisions.

Do not create a usage table. Do not reconstruct current bindings from activity history. Activity remains provenance and diagnostics, not operational authority.

Migration strategy

  1. Add the new tables, constraints, indexes, and immutable triggers in a new migration.
  2. Add one idempotent WorkspaceStore cutover operation guarded by a durable cutover row and one transaction.
  3. Materialize the currently activated genesis and Capability revisions into the new registry without changing their immutable refs.
  4. Convert each active WorkingAdjustment into one instruction Capability with a global/relevant binding by default. Preserve its original project and evidence as provenance; do not keep project scope merely because the old type required it.
  5. Keep historical WorkingAdjustment, Experiment, trial, preflight, activation-operation, observation, and outcome rows unchanged and readable in legacy audit sections.
  6. Stop enqueueing runtime.author_revision and runtime.preflight jobs after cutover. Let already-terminal jobs remain historical. Cancel or terminalize unfinished legacy jobs with an explicit cutover reason rather than silently abandoning leases.
  7. Switch turn planning to capability_bindings only after the cutover transaction is complete.
  8. Preserve import and decoder support for old rows. Do not dual-write old and new authorities.

Cutover is one-way operationally but non-destructive historically. Rollback means running the previous application binary against its still-readable old tables only if no new Capability binding has been created; once new writes exist, restore from the pre-cutover SQLite backup.

11. Implementation work

CAP-01Update doctrine and contracts

Replace narrow-first, recurrence-before-global, no-authority-expansion, and mandatory-preflight language. Define global/relevant defaults, always-active behavior, the tiny consequence gate, and recovery-first safety.

Acceptance: AGENTS and all three product documents describe the same behavior; historical plans are labelled historical rather than silently rewritten as current truth.

CAP-02Introduce Capability lifecycle schemas

Evolve domain types around Capability, immutable revision, one binding, feedback, and gate request. Remove evaluation-owned fields from the ordinary revision contract or make legacy decoding explicit.

Acceptance: strict unknown-data decoders, canonical digests, immutable lineage, and no parallel Change type.

CAP-03Add authoritative WorkspaceStore state

Add tables, constraints, indexes, immutable triggers, binding compare-and-swap, restore, pause, scope/mode mutation, feedback, gate settlement, and the idempotent legacy cutover.

Acceptance: crashes and retries cannot create two current bindings, overwrite a newer decision, mutate a referenced revision, or infer state from activity.

CAP-04Deepen packages/capabilities

Replace activation-plus-research coupling with the small lifecycle interface. Materialize exact predecessor and candidate bytes, validate adapters, preserve rollback, and expose read models.

Acceptance: instruction, skill, tool, workflow, router, configuration, and boot-safe core-update revisions exercise the same interface through real adapters.

CAP-05Simplify the learning organ

Replace WorkingAdjustment and Experiment decisions with Capability decisions. Run the reflector for every terminal turn. Ensure authoring receives exact predecessor materials and opened evidence. Implement iterateOnFeedback.

Acceptance: ordinary creation or revision uses at most reflection plus one author call; no_change needs no second call; no scope verifier or preflight work is scheduled.

CAP-06Replace coordinator pipeline

Retain one recoverable reflection/authoring job instead of reflection → author → preflight. Await only the exact prior-turn job before the next same-session turn. Terminalize legacy queued work at cutover.

Acceptance: process restart resumes one Capability iteration idempotently, and a failed learning job never changes the completed foreground turn.

CAP-07Route relevant and always-active capabilities

Add deterministic scope eligibility, direct inclusion for always, semantic selection for relevant, conflict validation, exact materialization, and frozen-plan pins.

Acceptance: an always/global Capability is present on every turn; a relevant/global Capability is selected only by the capable router; project/session scope cannot leak.

CAP-08Implement automatic activation and the tiny gate

Bind ordinary revisions immediately. Gate only the exact recovery and irreversible-consequence cases. Support approve, deny, and natural-language change with immutable pending refs.

Acceptance: global tools and authority configuration can activate automatically; a revision cannot erase its own audit or recovery; foreground intent does not produce duplicate approval prompts.

CAP-09Rebuild the learning read model

Make Capability the primary aggregate. Join exact revisions, predecessor diff, evidence, feedback, binding, gate, diagnostics, and legacy audit records. Derive usage only on explicit audit queries from frozen plans.

Acceptance: the default list contains material capabilities and pending decisions; routine reflection is one health summary; evidence is readable rather than an ID wall.

CAP-10Make /learning the management TUI

Extend the existing Pi TUI master-detail explorer with activate mode, scope, pause/resume, restore, approve/deny/change, exact diffs, notifications, and authoritative mutation settlement.

Acceptance: all operations work without transcript messages or notes; narrow and wide layouts remain usable; hostile terminal text is sanitized; shutdown truthfully settles or cancels interactive work.

CAP-11Remove the old production path

Remove new Experiment creation, dynamic preflight composition, protected-promotion scheduling, continuous-feedback outcome orchestration, WorkingAdjustment envelopes, and their live runtime dependencies. Retain historical decoding and audit projections.

Acceptance: production has exactly one learning mutation path and no dormant job runner can activate a legacy candidate after cutover.

CAP-12Prove recovery and real feedback iteration

Add acceptance flows using Pi AgentHarness and controlled providers: global capability creation, relevance selection, always-active override, user correction, child revision, restoration, pending-gate change, process restart, and broken-capability fallback.

Acceptance: the user can experience and correct a capability over consecutive turns, and every visible claim can be reconstructed from SQLite, immutable revisions, and frozen plans.

13. Explicit deferrals

  • Real evaluation system. No synthetic replacement is built here. A later design may execute exact baseline and candidate revisions in evaluator-controlled isolation.
  • Training model weights. This loop adapts the harness and creates high-quality preference data; it does not perform RLHF or fine-tuning.
  • Capability-use analytics. Frozen plans preserve derivability. Add a projection only when a real query cannot be served acceptably.
  • Confidence scores. Do not invent a scalar standing in for ambiguous evidence. Preserve evidence, feedback, and lifecycle decisions.
  • Automatic global narrowing from silence. Silence is not feedback. Scope changes require model-interpreted evidence or direct user intent.

14. Definition of done

  1. Capability is the only normal user-facing self-improvement abstraction.
  2. Every terminal foreground turn runs one ambient reflection without a usefulness pre-classifier.
  3. New capabilities default to global and relevant.
  4. The user can make any eligible Capability always active.
  5. The agent can autonomously activate global prompt, skill, tool, workflow, router, and configuration revisions.
  6. Ordinary learning schedules no experiment, preflight, trial, blind judge, or outcome judge.
  7. Explicit and ambient feedback can revise, pause, restore, re-scope, or change activation mode.
  8. The TUI offers approve, deny, and natural-language change only for the tiny consequence gate.
  9. Notifications are visible TUI chrome, not transcript messages or notes.
  10. The Capability aggregate does not store per-turn usage; frozen plans retain exact attribution.
  11. Previous revisions and a bootable recovery path remain available after every activation.
  12. Legacy learning records remain inspectable, but no legacy pipeline can create new live behavior.
  13. Current doctrine, implementation, tests, and /learning describe the same system.
