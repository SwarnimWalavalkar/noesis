Noesis · shipped implementation record

Process-scoped subagents

Turn subagents from synchronous nested model calls into asynchronous, retained collaborators that are orchestrated through Code Mode, communicate through durable mailboxes, survive session switches, and remain completely visible while Noesis is running.

process resident code orchestrated durable identity live inspectable no daemon yet

Decision

A subagent is a first-class Noesis actor with its own specialized session, stable agentId, sequential tasks, and durable mailbox. Its originating session is immutable provenance, not its lifecycle owner. A process-scoped supervisor runs agents until they settle, are explicitly cancelled, or the primary Noesis process exits.

Lifecycle owner

The primary Noesis process, not the parent turn, execute call, or session.

Orchestration surface

Only the progressively disclosed agents SDK inside execute.

Execution engine

Pi executes one agent task at a time; it does not become the product state authority.

Durable authority

SQLite owns agents, tasks, mailboxes, and settled transcript facts; artifacts own large bytes.

Product requirements

Asynchronous by default

agents.spawn durably admits work and returns a handle without waiting for completion.

Retained collaborators

An idle agent can receive another message and continue from its own prior conversation.

Bidirectional communication

Foreground sessions, parent agents, and sibling agents can exchange explicitly attributed messages.

Session independence

Switching, resuming, or creating a session never cancels work admitted by another session.

Complete observability

The user can watch reasoning, assistant output, messages, tool calls, Code Mode, usage, and failures.

Selective context

Child work stays outside the foreground context until code explicitly waits, inspects, or receives a report.

Boundary for this design

  • Noesis does not gain a daemon in this change.
  • Agents continue only while the primary Noesis process is alive.
  • Process shutdown interrupts active tasks truthfully; restart does not silently replay them.
  • No hard provider-round, tool-call, nesting-depth, or wall-clock ceiling is introduced.
  • Resource pressure may delay admission to execution, but it queues work rather than rejecting ambition.

Reference lessons, not copied architectures

  • Pi: keep AgentHarness as the executor of one task and use its safe steering boundary. Do not patch Pi or turn its in-memory session into Noesis's durable authority.
  • Prime Agent: adopt admission/completion separation, explicit agent messages, “busy means steer, idle means a new turn,” and child sessions. Defer its daemon, passivation, and hydration machinery.
  • pi-interactive-subagents: adopt immediate background spawn, visible workers, explicit messaging, and compact completion notices. Do not adopt tmux control, pane typing, session-file polling, or a sidecar registry.

Usage first

The model keeps one recursive programming surface. It uses ordinary JavaScript to create, coordinate, join, and synthesize work. No new provider-facing tool appears.

Parallel background work

const atlas = await agents.spawn({
  name: "atlas",
  systemPrompt: "Investigate the runtime and cite exact evidence.",
  prompt: context.slice(0, 80_000),
  tools: ["history.search", "history.open"],
  thinkingLevel: "high"
});

const sieve = await agents.spawn({
  name: "sieve",
  prompt: "Adversarially review the current design and report only concrete defects.",
  tools: ["files.read", "shell.run"]
});

// Both handles return after durable admission. This execution can return now.
({ atlas, sieve });

Communicate without joining

await agents.send({
  to: atlas.agentId,
  message: "Also compare behavior after switching sessions."
});

const running = await agents.list({ status: ["starting", "running", "idle"] });
running;

Join only when synthesis needs the result

const [runtime, review] = await Promise.all([
  agents.wait({ taskId: atlas.taskId }),
  agents.wait({ taskId: sieve.taskId })
]);

return synthesize(runtime, review);

Agent-to-agent reporting

// Inside a subagent's execute call:
await agents.send({
  to: agents.parent,
  message: "I found a recovery invariant worth checking; evidence is in packages/workspace/..."
});

Tool-free model-query behavior is still expressible as “spawn, then wait.” Every Pi actor retains the fixed four provider tool schemas; the frozen authority/catalog can make all operations unavailable when the caller wants an isolated reasoning task.

Domain model

IdentityMeaningLifetime
agentId A retained collaborator with stable route, system prompt, tool authority, and its own session. From spawn until explicitly closed or interrupted by process exit.
taskId One active unit of model work for that agent. At most one task runs per agent. Pending through one terminal outcome.
messageId One attributed mailbox message between foreground or subagent actors. Durable from acceptance through delivery or failure.

Agent identity, task identity, and message identity stay separate. A long-open tool call is never used as an actor, a task queue, or a mailbox.

interface AgentsApi {
  readonly self: AgentAddress;
  readonly parent?: AgentAddress;

  spawn(intent: SubAgentSpawnIntent): Promise<SubAgentHandle>;
  send(input: { to: string | AgentAddress; message: string }): Promise<MessageReceipt>;
  list(filter?: AgentListFilter): Promise<readonly SubAgentSummary[]>;
  inspect(input: { agentId: string; taskId?: string }): Promise<SubAgentInspection>;
  wait(input: { taskId: string; timeoutMs?: number }): Promise<SubAgentTaskResult>;
  cancel(input: { taskId: string; reason?: string }): Promise<SubAgentTaskResult>;
  close(input: { agentId: string; reason?: string }): Promise<void>;
}

agents.self and agents.parent are read-only, host-derived addresses. Callers cannot choose or spoof the sender recorded by send. A model-facing inspection returns a bounded recent preview plus the path, character length, and digest of a complete immutable transcript snapshot; the TUI reads the canonical rows directly.

OperationContractDoes it block on agent work?
spawn Freeze and durably admit the agent, initial message, and first task; return their IDs. No
send Durably enqueue one attributed message and return its delivery receipt. No
list Return bounded summaries for agents accessible in the current process and project. No
inspect Return bounded metadata, latest activity, task IDs, and complete transcript artifact reference. No
wait Join one exact task and return its terminal result. Cancelling the waiter only detaches it. Yes, deliberately
cancel Cancel one task. The retained agent becomes idle after truthful settlement. Only for settlement
close Stop active work if necessary and retire the actor from future messages. Only for settlement

The runtime derives the route from the user's configured subagent defaults. The spawning model may choose the system-prompt addition, thinking level, and a subset of canonical tools; it may not choose provider or model in this version. The frozen plan is immutable for the actor's lifetime. Changing those fundamentals creates a new agent instead of mutating an existing collaborator behind its transcript.

Lifecycle and message delivery

Spawn

  1. Validate the intent and resolve every ContextView against the active frozen document.
  2. Derive a child-only catalog and authority ceiling from the spawning actor.
  3. Freeze route, system prompt, reasoning, context budget, exact tool revisions, and origin.
  4. In one SQLite transaction, create the child session, actor, initial mailbox message, and task.
  5. Publish an admission event and return { agentId, taskId, status: "accepted" }.
  6. The process supervisor claims and starts the task independently of the spawning execution.

One active task per agent

Target state when a message arrivesBehavior
running The message is persisted immediately, then steered into the active Pi turn at its next safe boundary.
Agent starting or task pending The message joins the same task in FIFO order before or during its initial request construction.
idle The message creates the agent's next task and wakes the supervisor.
suspended or closed The send fails explicitly; it is never accepted into a mailbox that cannot deliver it.

“Next safe boundary” has the same honest meaning as foreground steering. A Pi tool already in progress finishes. An execute call is one Pi tool call, so a message accepted while that call is active waits until Code Mode returns unless the running program explicitly checks its mailbox. The TUI shows the message as pending rather than pretending it was consumed.

Completion

  • The final assistant message, usage, model rounds, and terminal task state settle durably.
  • The actor becomes idle and can receive another task.
  • An explicit agents.send report is delivered to its recipient mailbox.
  • If the agent ends without reporting, the origin receives only a compact lifecycle notification, not the full result.
  • agents.wait returns the exact task result without changing the task's lifecycle.

Messages addressed to a foreground session

  • If that session has an active model turn, the message becomes steering at the next safe boundary.
  • If it is the selected session and idle, the message may wake a collaboration turn immediately; the sender remains explicit and the body is not user-authored.
  • If another session is selected, the message stays pending. The TUI shows a process-wide notification, but Noesis does not run a hidden model turn in the inactive session.
  • Returning to the originating session exposes the pending message and lets its interaction scheduler deliver it.
  • A message for Session A is never injected into the currently selected Session B merely because B is visible.

Session and process behavior

EventEffect on active subagents
Originating foreground turn settles or aborts None. Admission already transferred lifecycle ownership to the process supervisor.
User starts or resumes another session Agents continue running. The process-wide TUI surface remains subscribed.
/model or /provider creates a fresh session Existing agents keep their frozen route and credentials; the new foreground route does not mutate them.
Origin session is deleted from history The agent continues. Minimal origin metadata remains as an audit tombstone while active evidence references it.
User explicitly cancels a task Only that task is cancelled; the actor may become idle and reusable.
User explicitly closes an agent Its active task is cancelled and the actor rejects future messages.
Primary process exits cleanly Supervisor aborts active tasks, records them interrupted, marks non-closed actors suspended, flushes events, then allows SQLite to close.
Primary process crashes Next startup reconciles ambiguous starting/running tasks to interrupted and their actors to suspended; it never assumes a provider or effect failed.
Noesis restarts History remains inspectable, but suspended actors are not automatically rehydrated or replayed in this design.

The supervisor is intentionally expressed through opaque IDs and durable repositories. A future daemon can host the same interface without changing Code Mode or the TUI read model. The daemon is a deployment relocation, not a prerequisite hidden inside this plan.

Tools, authority, and recursive orchestration

  • Every child Pi request exposes exactly file_read, file_write, shell, and execute.
  • The four schemas stay stable for prompt caching. The child catalog and authority determine which underlying operations can succeed.
  • tools in agents.spawn selects exact canonical Broker operations and revisions behind Code Mode; it never mutates the provider-facing tool set.
  • Messaging primitives are available through Code Mode and limited to the actor's accessible project/process family.
  • A foreground session can address any live agent in the same process and project. A subagent can address its parent, direct children, and siblings; broader reach requires an explicit handle passed by an authorized actor.
  • Recursive spawning is allowed only when the parent's frozen selection grants agents.spawn. There is no arbitrary depth limit.
  • Every descendant records its parent actor and immutable origin. Names are ergonomic aliases; IDs are authority-bearing identities.
  • Subagents remain advisory for self-improvement. Actor identity, not an ephemeral execution-ID set, prevents Capability publication.

Background authority

The current implementation reserves effects through foreground authority while the parent call is active. That cannot continue after the parent settles. Spawn must instead reserve a scheduler/background grant derived from the current frozen permission snapshot. The grant is an immutable ceiling: messages, later tasks, and recursive children cannot widen it.

  • Each provider round reserves and settles one durable network-cost operation.
  • Every child tool still crosses the canonical Broker, AuthorityBoundary, and EffectGateway.
  • Credential revocation and protected recovery controls remain live and can deny a later effect.
  • Effectful retries still require stable operation IDs and idempotency keys.
  • Scheduler backpressure may keep a task pending; it does not truncate model rounds or terminate productive work.

Message authority

A mailbox message never becomes a user-authored message merely because its recipient is a model. The provider context labels sender identity and treats the body as collaboration data. The recipient retains its own frozen authority, so receiving “delete this” from a sibling does not create fresh user intent or permission.

Transcript and event contract

A subagent's specialized session owns the same canonical kinds of transcript facts as a foreground session. The new runner must emit the complete event stream rather than forwarding only child tool calls.

Live, ephemeral deltas

Reasoning deltas, assistant text deltas, progress updates, and status motion.

Settled, durable boundaries

Reasoning messages, assistant messages, tool calls, model rounds, usage, mailbox deliveries, and terminal outcomes.

Large material

Prompts, full task results, complete derived transcripts, and oversized tool outputs remain artifact files with SQLite metadata.

Ordering rule

  1. Every settled child-session event receives one monotonic timeline sequence.
  2. The runtime persists the settled fact before broadcasting its durable event.
  3. The TUI hydrates through a sequence, subscribes from that cursor, and deduplicates by canonical ID.
  4. Live deltas reconcile into the later durable reasoning or assistant boundary.
  5. A dropped subscriber reloads from SQLite; it never asks Pi to reconstruct history.

One content authority

Mailbox content lives once in the mailbox record. Recipient transcripts contain an ordered delivery reference rather than a copied “user” message. Assistant and reasoning output lives in the child session's ordinary message records. Tool and Code Mode activity keeps canonical Broker IDs and gains agentId/taskId lineage. No parallel sub_agent_events transcript is introduced.

Reasoning visibility

  • Stream provider-visible reasoning when Pi emits thinking_delta.
  • Persist the settled reasoning boundary exactly as the foreground runtime already does.
  • Render “reasoning not exposed by this provider” when unavailable; never synthesize a substitute trace.
  • Reasoning remains presentation data, not a future instruction or conversation role.

Callers do not coordinate stores, Pi sessions, controllers, message claims, or transcript reconciliation themselves. That complexity stays behind one process-level module.

Persistence shape

AuthorityRequired data and constraints
sub_agents Agent ID; one unique child session; project and origin session/turn/execution; optional parent agent; immutable frozen-plan artifact/digest; lifecycle status; timestamps.
sub_agent_tasks Task ID; agent ID; triggering message; pending/running/terminal status; final message or result artifact; usage summary; timestamps; one running task per agent.
agent_messages Message ID; typed sender and recipient; content; sensitivity; FIFO sequence; accepted/claimed/delivered/failed state; optional task; timestamps.
Child sessions and ordinary transcript rows Assistant/reasoning messages, tool calls, Code Mode executions, and context checkpoints. Child sessions are excluded from normal resume/search surfaces unless deliberately queried.
model_calls One row per provider round with agent/task/round lineage, route, request/output artifacts, usage, cost, latency, and terminal status.
Artifacts Frozen plans, full prompts, full results, derived complete transcript files, and other large bytes with digests and relationship references.

Database invariants

  • A subagent's child session, project, origin, route, and frozen plan are immutable.
  • A task belongs to exactly one agent and the same project as its child session.
  • At most one task per agent may be pending or running.
  • A mailbox sender and recipient must exist and be visible within the admitted process/project scope.
  • Claim and terminal settlement use compare-and-swap transitions.
  • Tool, model, Code Mode, and message rows cannot cross agent/task/session/project lineage.
  • Terminal task state requires a settled timestamp and either a result or explicit failure/interruption reason.
  • Startup recovery changes ambiguous live states to interrupted without fabricating an effect outcome.

This is a deliberate breaking replacement for agents.run. Do not keep a compatibility adapter or a second nested-call execution path. Existing development-only rows may remain readable as historical legacy activity if that is cheap, but no new work uses them.

Failure semantics

FailureRequired outcome
Invalid prompt, context handle, tool name, or authority Spawn admission fails atomically; no orphan actor or task is created.
Provider authentication or setup fails after admission Task becomes failed with exact error; actor becomes idle and remains inspectable.
Provider outcome is ambiguous Task settles interrupted/ambiguous with unresolved effect receipt; never retry by assumption.
Tool call fails Canonical tool failure stays in the child transcript; Pi decides whether to continue.
Recipient is inaccessible, interrupted, or closed send fails explicitly before claiming successful delivery.
Waiting Code Mode execution is cancelled The waiter rejects and detaches. The target task keeps running unless separately cancelled.
TUI subscription drops or session changes Reload durable transcript/read models from the last sequence, then resume live events.
Individual message or result exceeds its typed context boundary Use an artifact/context reference and bounded preview; do not clip silently or limit the underlying task.
Process exits while tasks run Abort, settle interrupted, flush durable state, and stop. No background-survival claim.

Implementation sequence

  1. Types and authority. Introduce actor/task/message/frozen-plan contracts, scheduler grants, task-scoped model-call leases, and the provider-neutral task-runner port.
  2. SQLite authority. Add repositories, constraints, recovery, child-session filtering, task/model/tool lineage, and merged child transcript queries.
  3. Process supervisor. Build the closure-based scheduler, durable admission, mailbox claims, one-task-per-agent rule, waiters, cancellation, and shutdown reconciliation.
  4. Pi task runner. Replace the synchronous run adapter with one-turn execution that accepts steering and emits reasoning, assistant, tool, usage, and terminal events.
  5. Code Mode SDK. Replace agents.run with spawn/send/list/inspect/wait/cancel/close, preserve lazy context handles, and update the progressively loaded execute skill.
  6. TUI projection. Add the process-wide subscription, fixed active-agent surface, explicit inspect focus, completed-agent expansion, and live/hydrated transcript inspector.
  7. Removal and doctrine. Delete synchronous nested-call code, recursion sets, and old inspector branches; update product doctrine and mark superseded plan clauses clearly.

Acceptance boundary

Lifecycle

  • Two spawn calls return after durable admission and both tasks make progress concurrently.
  • The parent turn and its execute call may settle without cancelling either task.
  • Starting Session B while a Session A agent runs leaves it active and visible; returning to A restores its complete transcript.
  • Changing foreground model/provider does not change a running child's frozen route.
  • Clean process exit and crash recovery leave no authoritative task falsely marked running.

Communication

  • A message to a busy agent is visible immediately as accepted and becomes Pi steering at the next safe boundary.
  • A message to an idle agent starts a new task with the agent's prior session context.
  • Parent-to-child, child-to-parent, and sibling messages preserve sender identity and FIFO order.
  • No inter-agent message is persisted or replayed as user-authored content.
  • A completion without an explicit report creates only a compact lifecycle notification.

Orchestration and authority

  • spawn + wait covers the former isolated query and synchronous delegation cases.
  • Cancelling a waiter does not cancel the task it joined.
  • Every child exposes the same four provider tool schemas as the foreground agent.
  • Selected canonical tools and exact revisions, not provider tool mutation, control child access.
  • A child may recursively spawn only when granted that operation; productive work has no arbitrary call/depth/time ceiling.
  • Subagents cannot publish Capability changes, mint authority, or widen permissions through messages.
  • Every provider round and effect has a durable reservation, completion, and agent/task lineage.

Visibility

  • The fixed surface is process-wide, always shows active agents, and collapses idle agents and completed tasks by default.
  • Ctrl+O can navigate and open agents from inactive foreground sessions without skipping rows.
  • The live inspector streams reasoning, text, messages, tool progress, and nested Code Mode activity.
  • The resumed inspector reconstructs the same settled ordering from SQLite after switching sessions or restarting the TUI.
  • A provider that exposes no reasoning is labelled truthfully.
  • Child internals never appear in the main chat transcript.

Synthesis decision

The chosen shape combines a process-scoped actor supervisor with a specialized child session per agent. The supervisor hides scheduling, messaging, cancellation, and process lifecycle; the child session reuses Noesis's existing durable transcript, reasoning, tool, compaction, and inspection concepts. This is deeper than either a growing Code Mode API or a separate agent event system because callers see a small actor interface while the implementation owns all coordination behind it.

Alternatives considered

AlternativeWhy it lost
Make the existing nested agents.run call asynchronous Its prepared catalog, event sink, authority, cancellation, model-call row, and TUI identity all belong to a foreground execution that closes. Stretching it would preserve the wrong owner.
Keep background promises and agent objects inside Code Mode Generated JavaScript would own lifecycle and disappear when its child process exits. It would also create a second scheduler and uninspectable state.
Create separate sub_agent_events transcript storage It duplicates message, reasoning, tool, Code Mode, and ordering semantics that specialized sessions already own.
Launch separate Pi CLI processes in tmux, like the interactive extension reference The UX proves immediate spawn and visible workers are valuable, but pane typing, file polling, and sidecar registries bypass Noesis's Broker, SQLite, authority, and TUI read models.
Build the daemon now It adds transport, ownership, authentication, discovery, upgrade, and crash-supervision work before process-local behavior is proven. Opaque durable IDs keep that relocation available later.

Tradeoffs accepted

  • We accept that agents stop when Noesis exits in exchange for avoiding a premature daemon.
  • We accept one active task per agent in exchange for coherent retained conversation and deterministic mailbox ordering.
  • We accept that steering waits behind an atomic execute call in exchange for staying within Pi's safe turn/tool semantics.
  • We accept immutable route/system/tool fundamentals per actor in exchange for stable identity and reproducible history.
  • We accept a specialized child session per actor in exchange for reusing one transcript, context, compaction, and inspection architecture.

Deferred, deliberately

  • A daemon or launch agent that keeps work alive after the primary process exits.
  • Automatic replay or rehydration of interrupted tasks after restart.
  • Per-run provider/model override by the spawning model.
  • Mutable route, system prompt, or tool authority on an existing retained agent.
  • Remote or cross-device agent supervision.
  • A second provider-facing tool surface for agent management.
