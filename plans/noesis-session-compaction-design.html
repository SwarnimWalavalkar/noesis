Implementation design · decided

Durable session compaction

Compaction should reduce future model context without deleting, rewriting, or hiding the real conversation.

Starting point

Complete durable transcript

SQLite owns messages, tool calls, code runs, and their chronology. Resume rebuilds this full view.

Bounded turn context

Each turn creates a fresh Pi harness, so compaction belongs in durable context selection rather than Pi's ephemeral session.

An unfinished command

/compact existed in the TUI before the production runtime had durable compaction state.

Decisions

Append immutable context checkpoints and keep one active-checkpoint binding per session. A checkpoint preserves the useful meaning of older covered work so new work can fit; it does not promise full-fidelity replay inside model context.

  • Raw transcript rows remain untouched and searchable.
  • Compaction operates only on complete replay-eligible turn groups. It never splits a turn or includes running, aborted, failed, or partial work.
  • Each checkpoint has its own identity and digest, a model-written summary, its previous checkpoint ID, exact newly covered message references and their aggregate digest, the first retained raw turn, sensitivity, model route, usage, and creation time.
  • A future turn freezes the exact checkpoint ID, digest, summary material, and recent raw-tail references into its FrozenTurnPlan.
  • Repeated compaction writes a new checkpoint from the prior summary plus newly covered eligible work. It never edits an earlier checkpoint or repeats the full cumulative reference list.
  • After summary generation, checkpoint insertion and compare-and-swap of the active binding happen in one SQLite transaction. A failed or stale write changes neither.
  • Old frozen plans continue to cite the exact immutable checkpoint and raw context they used.

One context budget

The model-input budget is a number of tokens, not a message count or a percentage. It covers the complete request: system prompt, capabilities and tool allowance, checkpoint summary, retained raw conversation, and current input.

    "tokenBudget": 160000

}
  • context.tokenBudget is a positive integer. The built-in default is 160000 tokens.
  • The effective budget is min(configuredTokenBudget, model.contextWindow - outputReserve). It is therefore always smaller than the selected model's supported context window.
  • outputReserve comes from the resolved model's maximum output allowance. If the route cannot leave a positive input budget, model selection fails before a turn or compaction starts.
  • When a smaller model clamps the configured budget, Noesis reports the effective value instead of silently claiming the configured value was used.
  • The budget is one product setting. Noesis first reserves room for non-history request material, then uses the remainder for the checkpoint summary and recent raw tail. These internal allocations are not more user-facing knobs.
  • After a successful model response, its reported context usage is authoritative. Before provider usage exists, Noesis estimates roughly one token per four UTF-8 bytes. The estimate is deliberately provider-neutral; an OpenAI-specific tokenizer such as tiktoken would not give one sound answer for Anthropic, OpenCode, OpenRouter, and future routes.
  • The summary may use at most one quarter of the history allocation, capped at 8000 tokens.
  • Selection walks backward over complete turns until the raw-tail allocation is full. It never keeps a partial turn merely to fill the budget.

Compaction flow

  1. Read the active checkpoint, if any, and all later replay-eligible complete turns from SQLite.
  2. Select the largest recent complete-turn tail that fits the effective raw-tail allocation.
  3. Serialize every byte of each older newly covered turn as labelled data. A turn that cannot fit losslessly in the compactor route is rejected before model invocation and remains uncovered.
  4. Ask a capable model on the session's current route to update the structured summary. The previous summary is context, not a second authority.
  5. Validate and bound the summary. A summary cannot grant permission, raise instruction priority, or turn an old request into a new request.
  6. Insert the immutable checkpoint and move the active binding with compare-and-swap in one WorkspaceStore transaction.
  7. Future turns receive system context, the labelled checkpoint summary, the exact retained raw tail, and the current user input. Resume and history search continue to use the untouched transcript.

Triggers and interaction

  • /compact [optional focus] creates a checkpoint even before automatic compaction is required. Optional focus changes what detail the summary preserves; it does not change authority.
  • Automatic compaction runs before a future turn when eligible history would otherwise be omitted by the configured token budget.
  • Only one compaction may update a session at a time. A concurrent or stale attempt loses the active-binding compare-and-swap and leaves the winning checkpoint intact.
  • The successful TUI confirmation is simply Context compacted. Failure messages state that context was not changed.
  • If an active tool-heavy turn would exceed the complete-request budget, Noesis first projects older tool results into bounded references containing their tool identity, digest, byte count, and preview. This changes only the next model request. Full tool results remain durable and inspectable.
  • The first release does not add an automatic overflow retry. If the provider still rejects an admitted turn for context length, the turn fails truthfully and the user can retry after compaction.

Summary contract

The summary is a continuation handoff with bounded sections: goal, constraints and preferences, completed work, current state, key decisions, blockers, next steps, and critical references such as exact files, symbols, commands, and errors.

It is inserted as explicitly labelled reference context. The latest raw user message remains the only current request. Retrieved text, tool output, and prior user instructions inside the summary remain data at their original authority and sensitivity.

Failure semantics

  • If summary generation, validation, persistence, or compare-and-swap fails, the previous active checkpoint and raw replay behavior remain unchanged.
  • No deterministic fallback may drop turns or replace them with “summary unavailable.”
  • The first release admits only normal-sensitivity source material. Private or secret material fails closed before any compactor network request until an explicit provider sensitivity policy exists.
  • Cancellation propagates through model generation and stops before checkpoint activation.

Ownership and interface

WorkspaceStore owns checkpoint rows and the active binding. Runtime owns eligible-turn selection and frozen context. The app composition owns the capable-model call, authority, and usage recording.

compactSession(sessionId, { reason, instructions, signal })
resolveSessionContext(sessionId, modelRoute)

These are conceptual interfaces. Persistence mechanics, compare-and-swap, summary validation, and budget allocation stay behind the modules that own them.

Deferred

  • Semantic mid-turn or tool-pair summarization beyond bounded request-only tool-result projection.
  • Multiple compression engines or provider-specific compaction settings.
  • A dedicated checkpoint browser or approval flow.
  • Automatic retry of a provider-rejected foreground turn.
  • Compaction that deletes, archives, or changes the visible transcript.

Acceptance boundary

  • Resume still renders the complete original transcript.
  • Search still cites original authoritative rows.
  • Only future model context changes.
  • The checkpoint and retained raw tail fit the effective token budget, which is strictly below the selected model's context window.
  • The default and configured token budgets resolve consistently through config.json, startup, manual compaction, automatic compaction, and turn planning.
  • Provider-reported usage and the pre-response portable estimate use one token unit, and a budget failure reports the fixed, message, reported, trailing, and projected components.
  • Only complete replay-eligible turns can move behind a checkpoint.
  • Every checkpoint can be inspected. Replacement changes only the active binding and never edits an earlier checkpoint.
  • No summary can widen permissions or instruction priority.
  • A failed or cancelled compaction preserves the previous context selection exactly.
  • Repeated compaction consumes the previous immutable checkpoint plus newly covered work without quadratic provenance growth.
