The learning system, made legible

Users and builders can inspect how Noesis reflects, changes, evaluates, activates, observes, and learns without turning those records into a second source of truth.

Current surface

The old /learning command showed session activity and the current project strategy as flat text. The durable system contains much more: memories, routine reflections, working adjustments, experiments, immutable revisions, preflight and evaluation, activation, feedback, outcome research, outcomes, lineage, and orchestration jobs.

Smallest coherent product

/learning opens an inspect-only Pi TUI audit ledger. It shows every self-improvement primitive, including no_change reflections and routine jobs. Material changes remain easy to isolate through group filters, while the complete machinery stays available for product and architecture study.

Ledger

A dense chronological list groups memory, reflection, changes, evaluation, activation, feedback, and operations. It can narrow to the current session without losing the project-wide view.

Inspection

Each record exposes its exact identity, authority-derived status, project/session/capability context, evidence references, and typed lineage to related records.

Raw authority

The raw view is bounded and sensitivity-aware. Private or secret payloads remain redacted when the TUI has no admitted grant; missing relationships remain explicit instead of being guessed.

Decisions

  1. The active project is the default authority boundary. Current-session filtering is a view over that ledger, not a separate read model.
  2. Project strategies, experiments, revisions, evaluation records, activation records, feedback, and jobs share one list while retaining their own primitive kind and raw schema.
  3. no_change and routine jobs stay visible. Transparency means showing the machinery that decided not to change, not only successful adaptations.
  4. The first version is read-only. It does not create a durable Change object and does not infer current state from chronology.
  5. Terminal-controlled text is sanitized. Raw records are bounded, and sensitive raw payloads fail closed.

Remaining product questions

  1. After the inspect-only version, which protected action should ship first: unapply a project strategy, contest a lesson, or revert a durable revision?
  2. How should the TUI explain a change whose evaluation is still running without pinning transient status into the transcript?

Read-model boundary

The application composes one read model across authoritative criteria, jobs, adjustments, experiments, revisions, preflight plans and reports, trials, evaluations, activation operations and approvals, signals, observations, research, outcomes, and successor lineage. The read model creates no second durable Change authority. The Pi TUI renders it and owns no durable state. Missing links remain visible as incomplete data rather than being guessed from activity history.

  • Adjustment content comes from immutable working-adjustment rows; whether it is current comes from the active project binding.
  • Hypothesis, experiment state, source adjustment, and final outcome come from the authoritative experiment row.
  • Candidate material comes from immutable capability and file revisions. Evaluation evidence comes from trial, report, and evaluation rows.
  • Currently served durable behavior comes from activation state. Feedback comes from authoritative signals and outcomes.
  • Criteria and reflection jobs remain first-class so the user can audit what was remembered and why no change was made.
  • Coordinator jobs supply diagnostic progress only; they never override authoritative experiment, activation, or outcome state.
  • Current state and outcomes are never reconstructed from activity chronology, notices, or job history.

Future protected actions

A later unapply, contest, or revert control emits an application intent with the exact target revision and expected current state. AuthorityBoundary and EffectGateway validate and execute it as a durable operation. The overlay never writes operational tables, mints authority, or treats an optimistic UI update as completion.
