Noesis · implementation plan · research preview

Tools that compound

A single, inspectable architecture for thin self-modification tools, progressively disclosed skills, code-composed work tools, reusable scripts, and durable multi-phase workflows. The goal is not merely to give Noesis a shell. It is to give it a programmable action substrate that becomes more useful through use.

Status: historical implementation plan · core system shipped Runtime: TypeScript + Node + Pi Execution: JavaScript Authority: existing Noesis control plane

The direct-tool hotbar and separate public Script/Workflow API described below are superseded by noesis-programs-and-fixed-tool-surface.md. The shipped contract has a fixed four-tool provider surface and one public Program primitive with script and workflow execution modes.

The recommendation

Give the model one permanent programmable tool: execute. It executes JavaScript with Node.js on the user's machine and provides the work toolset as a programmatic SDK. Shell, files, web, session search, and future integrations are discoverable and composable through that SDK.

This preserves the user's desired context shape: the model always knows how to discover and improve itself through the built-in noesis skill, while a potentially enormous work toolset costs roughly one tool declaration. It also preserves Noesis's existing architecture: codemode is an execution client, not a second permission system, tool registry, persistence layer, or authority boundary.

The shipped default also keeps file read, file write with exact replacement, and shell run directly available for atomic work. Session search and generic workflow execution remain named inside execute; users may pin either deliberately through the Broker-backed operation taught by the built-in noesis skill.

Atomic tools

Host capabilities such as files.read, files.edit, shell.run, web.search, and history.search.

Skills

On-demand instruction and knowledge packages installed from the Agent Skills and Pi ecosystems. Skills teach; they do not create a second execution runtime.

Scripts

Saved, inspectable JavaScript programs for a reusable unit of work. “Script” describes an artifact, with no implication that it runs periodically or on a schedule.

Workflows

Durable, resumable multi-phase orchestration over agents and scripts. They own phase state while running as ordinary local Node programs.

Local Codex clone A fresh V8 isolate per cell; a persistent logical session; exec/wait; injected tools; a host delegate for nested calls; bounded IPC; cancellation; no Node, filesystem, or network globals. Reimplementing its Rust/V8 isolation stack. Take its simple model-visible tool, nested-call protocol, session lifecycle, and inspection ideas while using ordinary Node execution.
Local Hermes clone A child process, parent-owned tool dispatch, bounded calls/output, and a small RPC SDK. A hard-coded seven-tool allowlist and hand-maintained stubs. Noesis should derive its SDK and documentation from one catalog.

Noesis deliberately chooses trusted local execution for this research-preview iteration. Generated code is written to an ordinary .mjs entrypoint and launched with the user's installed Node.js. The child process exists for lifecycle, streaming, cancellation, and monitoring—not as a security sandbox. Node >= 22.19 remains a hard product requirement.

Be explicit about the trust model: generated scripts and workflows can use Node built-ins and locally available packages, and therefore can act with the user's local permissions. The Noesis SDK remains the preferred path because it gives the agent stable interfaces, structured results, citations, and excellent inspection. Strong containment is deferred until real usage demonstrates that it is worth the complexity.

Product and domain model

Term Meaning Authority
Noesis control tool A progressively disclosed Broker operation for inspecting or changing the harness, such as Capabilities or the direct-tool hotbar. Frozen Tool Catalog plus Broker and ordinary authority checks; guidance lives in the built-in noesis skill.
Skill A progressively disclosed instruction and knowledge package, compatible with the Agent Skills standard. It can include references, assets, and helper files. Installed skill files plus a frozen turn snapshot; Pi adapts discovery, prompt formatting, and explicit invocation.
Atomic tool One host capability with validated input/output and declared effects, such as reading a file or running a command. Canonical Tool Catalog plus host adapter. Model-accessible through codemode, or through the small direct hotbar when explicitly selected.
Codemode execution One local Node.js program written for the current turn. It can use ordinary JavaScript and Node while searching, describing, and invoking the frozen tool catalog through the Noesis SDK. Operational status in SQLite; code and result attached to the turn; nested effects recorded by the existing gateway path.
Script An inspectable, named, parameterized codemode program saved for reuse. A script is not automatically a skill. Editable definition files; immutable revision snapshots when invoked or evaluated.
Workflow A durable multi-phase program over agents and scripts with typed phase boundaries, progress, cancellation, and resume. Editable workflow definition; SQLite run and phase state; ordinary artifact files for large outputs.
Capability Noesis's broader unit of learned behavior. A capability may pin prompt, skill, tool, script, and routing revisions. Existing capability revision and activation system.
Experiment A proposed change under evaluation. It may produce a new script, tool, workflow, prompt, or capability revision. Existing experiment/evaluation/activation path. It is a process state, not another executable abstraction.
The key distinction: skills teach context and methods, tools provide atomic powers, scripts are reusable programs, workflows are durable orchestration, capabilities are learned behavior bundles, and experiments are how changes are tried. None of these names are aliases for one another.

The Tool Broker is the deepest new module. It hides catalog discovery, schema validation, frozen revision lookup, operation identity, permission binding, effect dispatch, result validation, and durable recording behind a small interface. Codemode and direct adapters do not recreate any of these decisions.

The broker seam

type ToolBroker = Readonly<{
  search: (
    scope: FrozenToolScope,
    query: string,
  ) => Promise<Result<readonly ToolSummary[], ToolBrokerError>>;

  describe: (
    scope: FrozenToolScope,
    toolName: string,
  ) => Promise<Result<ToolContract, ToolBrokerError>>;

  invoke: (
    scope: FrozenToolScope,
    request: ToolInvocationRequest,
    signal: AbortSignal,
  ) => Promise<Result<ToolInvocationResult, ToolBrokerError>>;
}>;

FrozenToolScope is host-created and contains the current principal, trail/turn, exact tool revisions, permission snapshot, and catalog digest. The child receives an opaque execution ID, and the host binds every nested SDK call back to the frozen scope. Node operations performed outside the SDK are covered by the enclosing local-code execution grant but do not produce structured per-call Noesis records.

Progressively disclosed harness control

Self-inspection and self-improvement use the same frozen Tool Catalog, Broker, and protected publisher as ordinary codemode work. They do not require permanently visible semantic tools or expose workspace paths, SQLite tables, authority receipts, or a second learning primitive.

capabilities.inspect

The single progressive inspector for learned behavior, bindings, lifecycle history, feedback, gates, and exact effect materials.

capabilities.refine

Publish a lasting fact, preference, criterion, or ability through the canonical Capability primitive. The host binds current turn evidence and authoritative versions automatically.

Hotbar mutation is not permanently model-visible. The built-in noesis skill teaches the foreground agent to discover and call noesis.hotbar through execute. Its exact schema comes from the frozen Tool Catalog.

Behavioral contract

  • The host supplies current principal, trail, turn, evidence, and provenance. The model supplies semantic intent.
  • Deliberate and ambient learning share the protected Capability publisher; no model-facing memory store competes with it.
  • noesis.hotbar inspects or changes the hotbar only. It is available only to the foreground agent's top-level execution and uses the same Broker and permission snapshot as every other catalog tool.
  • Ambient reflection is a separate process. It may produce no_change, which remains valid and should be common.
  • Ordinary user feedback such as “that was worse” is translated into evidence for ambient reflection and any broader protected consolidation; it is not a hidden hotbar mutation.
TUI self-modification begins with declarative themes, status widgets, and layout definitions. Arbitrary generated TypeScript must not run inside the TUI process. If arbitrary UI extensions become valuable, they use the same revision, evaluation, activation, and isolated execution principles as other generated behavior.

Skills: progressive knowledge and an open ecosystem

Agent-created executable behavior should normally be a workflow, not a skill. A skill is best understood as a discoverable package that teaches the agent when and how to approach a domain. A workflow is the inspectable executable behavior Noesis can create, evaluate, revise, and monitor. A skill may point to workflows, but it does not replace them.

Noesis should implement the Agent Skills standard by reusing Pi's existing skill primitives. Pi already discovers SKILL.md packages, validates frontmatter, represents skills as name/description/content/location, formats compact <available_skills> prompt metadata, resolves explicit skill invocation from the same frozen turn snapshot, and understands global, project, package, settings, and explicit-path sources.

Two origins, one skill experience

Origin What it becomes How it enters Noesis
User-authored or downloaded Agent Skill A standard SKILL.md package with instructions, references, assets, and optional helper scripts. Discovered from a configured directory or installed from npm, git, URL, or local path.
Noesis-created reusable behavior A workflow, or a script when a single program is sufficient. It receives the same compact discovery metadata and on-demand detail loading as a skill. Published immediately as a project-local definition through execute. Ambient reflection may later propose broader consolidation through the protected evaluation and activation path.
Noesis-created domain guidance Usually memory, prompt, or a workflow description. A generated SKILL.md is reserved for genuinely reusable instruction/reference material that should be portable to other Agent Skills-compatible harnesses. Proposed as an inspectable skill candidate, never silently conflated with a workflow.

Progressive disclosure

Level Always available Loaded when needed
0 · Discovery index Skill/workflow name, one precise description, scope, origin, and a compact input summary. Nothing else enters the context window.
1 · Instructions or contract Loaded after semantic match or explicit invocation. Full SKILL.md, or workflow description, inputs, outputs, phases, and required tools.
2 · Supporting resources Referenced only by Level 1 content. Specific references, examples, templates, assets, or source files requested through execute.
3 · Execution No executable bytes are placed in the model prompt. The exact script/workflow revision is invoked by execute and monitored as a run.

Agent and user invocation

  • At turn start, compact <available_skills> metadata remains in the prompt without presenting internal storage paths as project files. The always-visible execute tool description carries an analogous bounded, frozen <available_workflows> index containing only names and short descriptions.
  • When the agent recognizes a match, it calls execute and uses tools.skills.load({ name }) or tools.workflows.describe({ name }). The full content then returns through the normal tool loop.
  • A user can explicitly invoke /skill:<name> [arguments]. The Pi adapter uses AgentHarness.skill(), resolving the skill from the same frozen resources as the turn.
  • A user or agent invokes a workflow through /workflow:<name>, the workflow library, normal conversation, or noesis.workflows.run() inside execute.
  • The generic workflows.run runner is named in the execute contract. Each frozen saved workflow also appears under an exact, project-qualified Tool Catalog identity shown in the workflow index. Pinning it through noesis.hotbar exposes a friendly workflow_<name> tool with its typed contract, without creating another execution path or retargeting the pin across projects.

Installation and portability

noesis skills install npm:@scope/package@1.2.3
noesis skills install https://github.com/user/skill-repo@v1
noesis skills install git:github.com/user/skill-repo@commit
noesis skills install /absolute/or/relative/path
noesis skills install --workspace ./team-skills
  • Reuse Pi's exported DefaultPackageManager behind a runtime-pi adapter for npm, git, URL, local-path, install, update, remove, source resolution, and package dependencies.
  • Reuse DefaultResourceLoader and Pi skill parsing for standard locations and packages, configured through Noesis rather than creating another skill parser.
  • Support personal and workspace scope. Workspace entries take precedence by skill name; collisions remain visible in diagnostics and the TUI.
  • Also allow users to point Noesis at existing ~/.agents/skills, ~/.pi/agent/skills, ~/.claude/skills, and ~/.codex/skills directories instead of copying them.
  • Standard skills work without a Noesis-specific manifest. A package may additionally declare Noesis scripts/workflows, which are imported into the corresponding first-class libraries.
  • A skill's freeform scripts/ directory remains ordinary skill content unless an item declares a Noesis script manifest. This avoids confusing arbitrary helper files with first-class Noesis scripts.
  • Installing an online package shows one concise source preview: resolved source/ref, scope, included skills, included executable content, and dependencies. After installation it follows the same trusted-local Node model as user-authored code.

What Pi does—and does not own

Pi is the adapter for standard discovery, parsing, prompt formatting, explicit invocation, and package acquisition. Noesis freezes the exact skill bytes selected for a turn, records use and provenance, renders the library, and decides which workflow/tool/capability revisions are active. A downloaded Pi extension must not automatically register model-visible tools; executable integrations still enter through the one Noesis Tool Catalog.

Codemode: the programmable work surface

Yes—codemode is itself a basic agent tool. packages/runtime-pi registers execute as an ordinary Pi AgentTool. The model invokes it through the normal tool-calling loop. The difference is that the input is a JavaScript program and the program can make many nested calls through the generated SDK before returning one result.

Model-visible contract

await execute({
  source: `
    const files = await noesis.search("read and search project files");
    const contract = await noesis.describe("files.read");

    const matches = await tools.files.search({
      root: ".",
      query: "TODO",
      glob: "**/*.ts"
    });

    const contents = await Promise.all(
      matches.slice(0, 20).map((match) =>
        tools.files.read({ path: match.path })
      )
    );

    return contents.map(summarizeLocally);
  `
});

JavaScript is the execution language even though Noesis is authored in TypeScript. Noesis writes a temporary .mjs entrypoint and launches it with the user's Node.js. The host generates TypeScript-like declarations and examples for the SDK, but no compilation step is required.

Local execution surface

  • tools: namespace of callable proxies resolved through the broker.
  • noesis.search(query) and noesis.describe(name): progressive tool discovery.
  • noesis.step(name, fn): a stable replay boundary for effectful or resumable work.
  • scripts.list/describe/run: saved programs, added after the script workstream.
  • emit(value), notify(value), and exit(value): bounded result and progress helpers.
  • JSON-safe session storage through store/load, scoped to the current Noesis trail and codemode session.
  • Ordinary Node.js globals, built-ins, dynamic imports, and locally installed dependencies. The working directory is the task's declared cwd.

The agent is instructed to prefer tools.* for user work: SDK calls are typed, searchable, cited, rendered live in the TUI, and recorded for learning and replay. Direct Node operations are permitted in this trusted-local iteration, but they have only process-level stdout/stderr and exit observability.

Initial atomic tool families

Namespace Initial tools Notes
files list, search, read, write, edit, apply_patch, stat Workspace-relative paths by default; explicit roots can be granted. Results cite paths and revisions.
shell run, write_stdin PTY and non-PTY, abortable, bounded output, stable process handles, explicit cwd.

artifacts create, read, attach Large outputs stay in ordinary files with SQLite metadata.

Invocation semantics

  1. Freeze the exact tool catalog and permissions at turn start. A running cell cannot discover a newly activated tool revision.
  2. Validate nested input with Zod before any reservation or effect.
  3. Derive effect class, resource, cost, and operation fingerprint host-side. Generated code cannot choose them.
  4. Record the request and reserve effect use durably before dispatch.
  5. Dispatch through EffectGateway; credentials and grants remain host-side.
  6. Validate, normalize, bound, and record the result before returning it to the running Node program.
  7. Expose only the value selected by the script to the model context. Full nested lineage remains inspectable from the execution record.
A codemode execution is not a transaction across the outside world. If a script performs three effects and the fourth fails, the first three remain real. Completed steps replay from their recorded results; an interrupted effect with no unambiguous outcome fails closed. Compensation is explicit and tool-specific, never implied rollback. Direct Node operations cannot receive this per-call replay behavior.

Scripts: successful code that becomes reusable

A script is the smallest reusable unit above an atomic tool. During explicit foreground work, the user or agent may save and publish one directly for this project. It is immediately usable through execute under current authority. Reflection may observe later runs and propose broader learned consolidation when evidence recurs.

Inspectable definition

definitions/scripts/projects/<project-id>/repo-health/
  script.json   # name, description, input/output JSON schemas, tool requirements
  index.mjs      # program body invoked with { input, tools, noesis }

revisions/scripts/<revision-id>/
  script.json   # byte-stable snapshot
  index.mjs      # byte-stable snapshot

The editable files are authoritative for the working definition. Every execution pins an immutable recorded revision. Editing the working file never changes an in-flight or historical run.

Lifecycle

ad hoc code succeeds
  → user asks "save that" or the foreground agent identifies project reuse
  → materialize and validate a project-local definition
  → publish it to codemode as scripts.run(...) under current authority
  → use it immediately through execute
  → collect task outcome and conversational feedback
  → inspect, edit, or replace locally; evaluate only broader learned consolidation
  • Scripts declare required tool names and effect classes. The run still uses the caller's current frozen permissions.
  • Scripts receive structured JSON input and must return a value that passes their output schema.
  • Scripts may import Node built-ins and dependencies already installed in the Noesis or target workspace. Automatic dependency installation is not part of the first implementation.
  • Skills remain instructional context and may refer to scripts later. Script and skill are intentionally not the same abstraction.

Workflows: durable thinking and doing

A workflow is warranted when work must survive a turn, expose phase progress, pause, resume, or accept feedback between phases. It is not merely a long codemode cell. The first implementation is deliberately sequential; bounded fan-out and background scheduling remain later extensions.

Programming model

await tools.workflows.save({
  name: "deep-research",
  description: "Discover, analyze, and synthesize in durable order.",
  inputSchema: { /* JSON Schema */ },
  outputSchema: { /* JSON Schema */ },
  phases: [
    { name: "discover", source: "/* return a source list */", /* schemas + requiredTools */ },
    { name: "analyze", source: "/* analyze the complete list */", /* schemas + requiredTools */ },
    { name: "synthesize", source: "/* produce the final answer */", /* schemas + requiredTools */ }
  ]
});

Workflow rules

  • Workflow definitions are ordinary local Node programs. Their agent, script, and tools helpers use the same Tool Broker and Effect Gateway; direct Node operations remain possible under the workflow's enclosing execution grant.
  • phase(name, schema, fn) is a stable durable step: requested, running, completed, failed, ambiguous, or cancelled.
  • Phase input/output is schema-validated. Large data becomes an artifact reference rather than an oversized SQLite blob.
  • Phases execute sequentially in the first implementation. A later bounded map primitive may use the existing job scheduler; workflows will not introduce another queue.
  • Resume reuses completed phase outputs. An ambiguous effect blocks automatic continuation until reconciled.
  • A workflow run pins its definition, capabilities, model routing, tool catalog, and the visible project script/workflow library. Until manifests declare exact saved-definition dependencies, any library edit conservatively blocks resume rather than silently switching executable code. Later edits always affect later runs.
  • User feedback can be an explicit phase input, a conversational correction, or post-run outcome evidence.

Skills, scripts, and workflows as first-class TUI objects

The TUI must make the programmable substrate feel like part of the product, not a hidden developer feature. A user should be able to move naturally between conversation, reusable definitions, and live work without leaving Noesis.

Primary surfaces

  • Foreground codemode collapses to a live summary such as execute · 8 calls · 6 read · 1 write · 1.2s.
  • Pressing Enter on that summary opens a run inspector with source, inputs, stdout/stderr, returned value, nested SDK calls, durations, errors, artifacts, and effect receipts.
  • /skills opens a searchable skill library with personal and workspace scope, origin, compatibility, installed revision, diagnostics, and included resources. The detail view renders SKILL.md, references, assets, provenance, and related scripts/workflows, with invoke, install, update, remove, enable, and inspect actions.
  • /scripts opens a searchable script library. The list shows name, description, origin, revision, last run, recent success, and required tools. Its detail view shows formatted source, manifest, revision history, provenance, recent runs, and actions to run, edit, compare, or inspect.
  • /workflows opens a searchable workflow library. Its detail view shows the phase graph, schemas, source, pinned dependencies, revisions, recent outcomes, and actions to start, edit, clone, or inspect.
  • /runs opens active and recent script/workflow runs. Active workflows show phases, current activity, fan-out, elapsed time, model/cost where available, logs, artifacts, and pause/cancel/resume controls.
  • The command palette exposes the same library, run, and inspection actions, and transcript rows deep-link into the relevant script, workflow, revision, or run. Navigation must be keyboard-first and preserve the current chat state when the user returns.
  • Conversational commands remain primary: “save that,” “run it again,” “continue in the background,” and “change the synthesis phase.”
UX principle: source, definitions, and run history are not debugging afterthoughts. Skills, scripts, and workflows are user-owned objects. Their library and inspector surfaces ship with execution, backed by TUI read models rather than UI-owned durable state.

Extend the existing one-authority matrix; do not create an event-sourced shadow state. Activity records explain what happened. They do not reconstruct current operational truth.

Implementation workstreams

TCW-00 Freeze the vocabulary and prove the Node runner lifecycle

Outcome
A minimal local Node runner proves the process and SDK protocol before package interfaces or migrations are committed.
Work
Execute .mjs files; inject execution identity and SDK client; bridge sequential and parallel host calls; stream stdout/stderr and progress; bound captured output and SDK call count; cancel outstanding calls; and prove clean process shutdown.
Gate
Do not design multiple runner adapters. Adopt the ordinary Node child process once async SDK calls, cancellation, streaming, and shutdown are proven.

TCW-01 Build the one canonical Tool Catalog and Broker

Outcome
One package defines discovery and invocation for all atomic tools. The current session-search tools move behind it.
Work
Define functional Zod-backed tool definitions, visibility (always or codemode_only), frozen catalog snapshots, search, describe, invocation, normalized errors, bounded/cited results, and adapter injection. Integrate EffectGateway rather than recreating it.
Acceptance
A caller can freeze a catalog, search it, describe one revision, invoke it through a scripted adapter, and prove that later catalog mutations do not affect the frozen call.

TCW-02 Implement the codemode process and session

Outcome
packages/codemode runs local Node.js cells and delegates SDK calls without knowing what any real tool does.
Work
Child-process host, framed JSON protocol, session/cell IDs, execute/wait/terminate/shutdown, generated .mjs bootstrap, SDK client, JSON-safe session store, stdout/stderr/result streaming, pending call limits, backpressure, and abort propagation.
Acceptance
Pure computation, sequential/parallel delegate calls, progress, ordinary Node imports, timeout, cancellation, malformed frames, child crash, and orderly app exit all have deterministic tests.

TCW-03 Add authoritative execution records

Outcome
SQLite owns codemode execution/cell status and nested call lineage; ordinary artifacts own large code and output.
Work
Add migrations and WorkspaceStore functions for executions, cells, stable steps, parent-child tool calls, cancellation, and ambiguous outcomes. Extend existing rows rather than creating parallel effect history. Add integrity checks and read models.
Acceptance
Restart rehydrates terminal and interrupted execution state without guessing. An unresolved reserved effect remains blocked.

TCW-04 Ship the first useful work toolset

Outcome
Codemode can inspect and modify a project, run commands, search the web, search Noesis history, and create artifacts.
Work
Implement or adapt the initial files, shell, web, history, and artifacts families. Prefer Pi's proven coding primitives behind a narrow runtime-pi adapter where they fit; Pi types must not escape that package. Add stable process handles and abortable streams.
Acceptance
A controlled Pi turn completes the repository-TODO journey with one model-visible codemode call and inspectable nested operations.

TCW-05 Implement progressive harness control

Outcome
The agent can inspect and refine active Capabilities and deliberately inspect, add, or remove exact frozen Tool Catalog entries from its direct-tool hotbar without seeing storage internals.
Work
Expose capabilities.inspect, capabilities.refine, and noesis.hotbar through the frozen catalog, and teach them only in the progressively disclosed built-in skill. Bind provenance and authoritative context host-side for learning operations.
Acceptance
Capability inspection and publication use one protected primitive; inspecting, adding, or removing a tool uses the same Broker and updates the direct hotbar and its persisted preference without widening authority. Ambient reflection may separately produce no_change or a broader candidate, while explicit foreground script publication uses the direct project-local path.

TCW-06 Integrate the frozen turn and Pi surface

Outcome
Pi sees execute and the small atomic direct hotbar; the code session sees the frozen catalog.
Work
Extend FrozenTurnPlan with exact catalog/permission identity, compose the broker at the application root, keep session search codemode-only by default, stream nested activity through existing runtime events, and close code sessions during normal shutdown.
Acceptance
Plain startup, completed turns, /quit, Ctrl+C, --continue, abort, and process error all release the executor without hanging or losing authoritative state.

TCW-07 Make codemode legible in the TUI

Outcome
Work feels active but not noisy. The transcript shows a compact summary with a discoverable detailed inspector.
Work
Add execution read models, live aggregate status, nested call counts, transcript deep-links, the reusable run inspector, /runs library, error/cancellation states, and bounded source/result/stdout/stderr previews. Establish reusable list, detail, revision, and run-inspection views that TCW-08, TCW-09, and TCW-10 populate. Preserve markdown/LaTeX rendering and native input behavior.
Acceptance
Long-running and high-volume executions remain readable at narrow and wide terminal sizes; keyboard navigation enters and leaves the inspector without losing chat state; the model transcript contains only the selected final value.

TCW-08 Add the skill library and Pi package installation

Outcome

Serialization points

  • TCW-00 is a short gate because child-process behavior shapes protocol and lifecycle; it is not a sandbox research project.
  • TCW-01 first freezes the broker contracts; TCW-02, TCW-03, and TCW-05 can then proceed in parallel against those types.
  • TCW-06 is the integration barrier. No work tool becomes model-visible through a separate temporary path.
  • Skills and scripts can build in parallel after the frozen resource and TUI seams are proven. Workflows follow a proven script revision and reuse the existing scheduler.
  • Self-improvement closes last because it needs real execution and outcome evidence. Its progressive inspection tools can ship earlier.

Suggested implementation task ownership

After TCW-00, separate tasks may own: (A) Tool Broker and work adapters, (B) codemode runtime/protocol, (C) WorkspaceStore migrations/read models, and (D) progressive harness-control behavior. TCW-06 should be one integration owner. Skills and scripts may proceed in parallel; workflows should be a stacked follow-up rather than a parallel edit to the same runtime composition.

Verification and product journeys

Contract tests

  • Node version, cwd, module resolution, SDK injection, the enclosing execution grant, stdout/stderr streaming, and exit behavior are explicit and reproducible.
  • Too many SDK calls, huge captured output, cancellation, malformed IPC, and child crashes terminate predictably.
  • Every nested input and output is validated at the broker boundary.
  • Frozen catalog, tool, skill, script, workflow, prompt, and permission revisions are byte-stable for a run.
  • Effect identities collide safely; ambiguous outcomes fail closed; completed named steps replay without repeating effects.
  • Executor shutdown is included in both /quit and Ctrl+C after completed and interrupted turns.
  • Script, workflow, and run libraries remain responsive, searchable, keyboard-navigable, and correctly deep-link to source, revisions, phases, nested calls, logs, artifacts, and receipts.

Required checks

Every implementation stack runs pnpm format, pnpm lint, pnpm typecheck, and pnpm test. Product journeys use the credential-free controlled Pi provider path and the actual runtime composition; no fake production runtime is reintroduced.

Explicit non-goals for the first complete implementation

  • Security sandboxing or container isolation for local generated code.
  • Automatic installation or mutation of npm dependencies.
  • A second tool registry for codemode or workflows.
  • A second permission, approval, effect, scheduler, or persistence system.
  • Direct model exposure of the broad work tool catalog.
  • Automatically enabling Pi package extensions or bypassing the Noesis Tool Catalog.
  • Automatic rollback of arbitrary external side effects.
  • Equating scripts with skills or forcing all reuse through skills.
  • Arbitrary generated TypeScript in the TUI process.
  • Cloud-only execution as a requirement for local Noesis.
  • Restoring the deleted duplicate tool runtime without this broker path replacing its responsibility.

Definition of done

Noesis can install and progressively load portable Agent Skills; complete real local and web work through one model-visible execute tool; inspect and refine its active behavior through one Capability primitive, and manage its direct-tool hotbar through one progressively disclosed Broker operation; save successful programs as inspectable scripts; run typed multi-phase work durably; and learn from the outcomes without creating duplicate authority systems.

The feature is complete only when a user can understand what ran, what changed, which exact revisions were used, what evidence supported an adaptation, and how to contest or revert it—without the ordinary experience becoming a procession of approval dialogs.

This plan extends the product thesis, product experience, first-complete iteration, autonomous-compounding architecture, and compounding partnership loop. Where those plans previously deferred generated tools, the user's explicit need for a real programmable work surface now satisfies the “proven need” condition—but only through one authoritative execution spine.
