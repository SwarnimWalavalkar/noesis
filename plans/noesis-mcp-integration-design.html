Design workshop · open

MCP as one more tool source

MCP should extend Noesis's frozen Tool Catalog. It should not create a second execution path beside the Broker.

Proposed first boundary

A host-owned MCP connection manager reads declarative server definitions and projects discovered tools as namespaced Broker definitions such as mcp.github.search_code. Launch, connect, authenticate, discover, reconnect, and shutdown are protected, recorded effects rather than an execution path around the Broker.

Transports

Start with stdio and Streamable HTTP.

Surface

Tools only. Defer prompts, resources, roots, sampling, and elicitation.

Lifecycle

The connection manager requests launch, connect, authenticate, discover, reload, reconcile, and shutdown through AuthorityBoundary and EffectGateway. Each is a separate durable operation.

Invocation

Only admitted MCP tool calls use ToolBroker. The execute SDK and hotbar invoke the same descriptor through the same frozen Broker, permissions, and durable call path.

A project-local definition is inert until the user trusts its exact immutable normalized revision. The trust record binds the definition digest, transport, executable and arguments or remote URL, and credential references. Editing any bound field creates a new revision that is not trusted yet. Discovery produces a catalog snapshot before admission. Refresh and reconnect may change only a future turn's frozen catalog, never the catalog of a running turn.

Each lifecycle effect has a stable operation ID and idempotency key bound to the server, operation, trusted definition digest, and request identity. An incomplete effect is reconciled from durable state; it is never retried by assuming it failed.

A discovered tool's immutable revision identity binds the trusted server-definition digest, discovery-snapshot digest, canonical descriptor and schemas, transport and endpoint identity, and credential references. Credential values are resolved only at execution from the protected credential store or process environment. They never enter definitions, trust records, snapshots, catalog descriptors, transcripts, or TUI read models.

Server names, descriptions, schemas, errors, and result text are bounded and credential-redacted at the external boundary and remain untrusted data. They may describe Broker tools or appear in tool results, but they never become system instructions.

Failure and publication

  • Each server has an independent lifecycle state. A failure quarantines only that server and makes its new calls fail closed.
  • The last-known-good immutable discovery snapshot remains available for inspection and for already frozen turns.
  • A refresh validates the complete new snapshot before atomically publishing a replacement catalog for future turns. Partial discovery never changes a catalog.
  • An ambiguous launch, connection, or shutdown remains unresolved until reconciliation proves its outcome.

Decisions we need

  1. Should server definitions live in ~/.noesis/config.json, a dedicated editable mcp.json, or project files?
  2. How should the user inspect and grant trust to an exact normalized definition revision before its bound process or URL is used?
  3. Which credential forms ship first: environment references, bearer tokens, or full MCP OAuth?
  4. How are arbitrary MCP JSON Schemas validated and adapted to the Broker's Zod boundary?
  5. How are text, images, embedded resources, and large results mapped to JSON values or artifacts?
  6. What effect class and resource identity should each discovered tool receive?
  7. What triggers a between-turn catalog refresh: explicit reload, reconnect, or startup health checking?

Product surface

  • /mcp renders a WorkspaceStore and SQLite-backed read model of trusted revisions, lifecycle operations, health, quarantine, discovery snapshots, tool count, and bounded last errors.
  • A server detail overlay lists discovered tools and their descriptions.
  • Tool calls flow through the normal transcript and run inspector.
  • One broken server does not prevent other servers or local tools from working.
  • Trust, reload, reconcile, and shutdown are application intents executed through AuthorityBoundary and EffectGateway. The TUI owns no MCP client or durable state.

Non-goals for the first build

No automatic installation from untrusted content, no trust that survives a changed definition digest, no direct Pi MCP registry, no silent permission widening, no external server text in the system prompt, and no attempt to cover the entire MCP protocol at once.
