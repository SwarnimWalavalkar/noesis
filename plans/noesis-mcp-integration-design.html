Implementation design · revised

MCP should just work

Install a server, authenticate it when needed, and use everything it provides. Noesis should be a fully compatible MCP host with excellent discovery and TUI management—not a partial protocol adapter.

Product contract

/mcp is the home for installing, authenticating, enabling, disabling, inspecting, reconnecting, and removing MCP servers. Once enabled, a server's capabilities are available to the model and to workflows; project servers also require a trusted workspace.

Compatibility

Implement the complete MCP client surface supported by the official TypeScript SDK: tools, prompts, resources and templates, roots, sampling, elicitation, completions, subscriptions, logging, progress, cancellation, notifications, OAuth, and tasks.

Transports

Support local stdio and remote Streamable HTTP. Retain legacy SSE interoperability where the SDK can negotiate it.

Configuration

Read global servers from ~/.noesis/mcp.json and project servers from ./.noesis/mcp.json. Project entries override global entries with the same name.

Authentication

Implement the full MCP OAuth flow, including discovery, dynamic client registration where supported, browser callback, refresh, logout, and pre-registered client credentials.

Simple architecture

A host-owned MCP manager uses the official SDK to load the merged configuration, connect enabled servers, negotiate capabilities, and keep their live clients. Installing or enabling a server is the user's authorization to connect to it. There is no separate trust ceremony or digest approval flow.

MCP remains one capability source inside Noesis:

  • Discovered tools become ordinary frozen Tool Catalog entries named mcp.<server>.<tool>.
  • The same Broker invocation path serves execute, direct hotbar tools, and workflow phases.
  • Prompts, resources, templates, and completions remain native MCP capabilities exposed through the same host manager and SDK.
  • Roots expose the active project by default. Sampling uses Noesis's current model routing. Elicitation opens an interactive form or URL flow in the TUI.
  • Progress, logs, cancellation, task state, and server requests appear in the normal live action stream and remain inspectable with the work they belong to.
  • Server instructions are surfaced as clearly delimited server-provided context. They can guide use of that server but do not replace Noesis's own instructions.

Progressive discovery

The model must be able to discover every enabled MCP capability without placing every schema in its context window.

Compact index

The always-visible execute context includes enabled server names, short descriptions, capability counts, and canonical namespaces.

On demand

The execute SDK can list and search tools, inspect one tool's full schema, list or fetch prompts, list or read resources, and inspect server capabilities before use.

Direct use

Any MCP tool may be pinned to the hotbar as a regular direct tool. Its full schema is disclosed only while pinned.

Workflows

Workflows reference canonical names such as mcp.github.search_code in requiredTools and invoke them through the same frozen Broker.

Configuration

{
  "servers": {
    "github": {
      "type": "remote",
      "url": "https://api.githubcopilot.com/mcp/",
      "enabled": true,
      "oauth": true
    },
    "filesystem": {
      "type": "local",
      "command": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "."],
      "enabled": true
    }
  }
}
  • The global file contains personal servers available everywhere.
  • The project file adds or overrides servers for that project.
  • Project servers remain inactive until the workspace is trusted; global user-owned servers are unaffected.
  • /mcp can write an installation to either scope. The files remain ordinary editable JSON.
  • OAuth tokens live in Noesis's credential store. Configuration stores only server settings, environment references, and optional OAuth client metadata—not access or refresh tokens.
  • Changes, explicit reload, startup, reconnect, enable or disable, and MCP listChanged notifications all refresh discovery. A running turn keeps its frozen tools; the refreshed catalog is used by the next turn.

Schema and result handling

Keep MCP JSON Schema as JSON Schema. Do not build a lossy JSON-Schema-to-Zod compiler. The protocol SDK validates MCP envelopes; the Broker accepts a JSON object at its runtime boundary and publishes the server's original input schema to the model. This follows OpenCode's practical approach of adapting native MCP schemas directly, while Hermes likewise registers discovered schemas without introducing a second type system.

Return the native MCP result shape: content blocks, structured content, resource links, and embedded resources. Text renders as text; images and other content remain typed blocks; large payloads use Noesis's existing artifact storage automatically. There is no MCP-specific result format.

Names and execution identity

  • Tools use mcp.<server>.<tool>. Other capabilities use the same server namespace in the SDK and TUI.
  • The execution resource is mcp:<scope>:<server>:<capability>. Remote calls use the existing network effect; local stdio calls use the existing execute effect. No new MCP-specific effect classes are needed.
  • MCP side effects use the existing AuthorityBoundary and EffectGateway. Lifecycle operations and reverse sampling use stable operation identities, durable reservations, and fail-closed reconciliation.
  • Reconnect retries restore transport lifecycle only. An ordinary MCP tool effect with an incomplete or unknown outcome is never called again automatically unless the protocol provides an explicit idempotent task-resumption contract.
  • Frozen tool identity includes the server configuration, discovered schema, and tool name so resumed workflows execute the same capability they started with.
  • Reverse sampling is accepted only when it is bound to an admitted MCP invocation. It uses that turn's frozen model route and protected effect budget.
  • One failing server does not hide healthy servers or built-in tools. Reconnect and discovery retry independently.

/mcp TUI

Keep the UI centered on the user's actual jobs: install, authenticate, use, enable, disable, and remove.

  • The main view lists installed global and project servers with enabled, connected, authentication-required, or failed status.
  • Add server accepts a local command or remote URL and asks whether to save it globally or in the project.
  • Authenticate opens the browser OAuth flow and returns to the server row when complete.
  • Server-requested URLs show their domain and full address first, and open only after explicit user acceptance.
  • Enable/disable, reconnect, edit, and remove are actions on the selected server.
  • Opening a server enters a nested detail view for its tools, prompts, resources, templates, server instructions, connection details, and recent errors.
  • Opening a tool, prompt, or resource shows its full description and schema or metadata.

Complete compatibility checklist

Server capabilities

Tools, prompts, resources, templates, completions, subscriptions, list-changed and resource-updated notifications, logging, progress, cancellation, and experimental tasks.

Client capabilities

Roots and roots-changed, model sampling, form and URL elicitation, multi-round input-required flows, and task-augmented requests.

Remote auth

Protected-resource discovery, authorization-server discovery, PKCE, browser callbacks, dynamic registration, pre-registered clients, token refresh, logout, and URL-bound credential lookup.

Protocol behavior

Capability negotiation, pagination, notifications, cancellation, timeouts, reconnect and resumption, progress tokens, structured output, and compatibility across supported protocol revisions.

Reference lessons

  • Hermes: simple namespaced discovery, long-lived connections, automatic reconnect, and a management UI are good product defaults.
  • OpenCode: native JSON Schema adaptation, local and remote configuration, enable/disable, OAuth with dynamic registration, and native prompts/resources are the right compatibility baseline.
  • Noesis: add progressive disclosure, full transcript visibility, hotbar pinning, and first-class workflow composition without inventing a second MCP execution system.
